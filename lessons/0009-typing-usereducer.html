Typing useReducer

~7 min · Builds on: Lesson 2 (discriminated unions) · Lesson 5 (context) · Glossary

← Exercise 2: Context & Utility Types Next: Forms & Actions

When state transitions get complex — multiple fields updating each other, undo/redo, wizard flows — codebases reach for useReducer. Typing it is mostly Lesson 2's discriminated union applied twice: once to the state, once to the actions.

The three pieces

import { useReducer } from "react";

interface State {
  count: number;
}

// The action union — every legal transition, named:
type Action =
  | { type: "reset" }
  | { type: "setCount"; value: number };

const initialState: State = { count: 0 };

// Fully annotated — this is where the types live:
function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "reset":
      return initialState;
    case "setCount":
      return { ...state, count: action.value };
  }
}

export default function Counter() {
  const [state, dispatch] = useReducer(reducer, initialState);

  // dispatch is typed automatically — no annotation:
  const addFive = () => dispatch({ type: "setCount", value: state.count + 5 });
  const reset = () => dispatch({ type: "reset" });

  return (
    <>
      <p>Count: {state.count}</p>
      <button onClick={addFive}>+5</button>
      <button onClick={reset}>Reset</button>
    </>
  );
}

Notice what you don't write: useReducer<State, Action>. You annotate the reducer itself, and inference flows from there:

  • dispatch gets the type React.Dispatch<Action>
  • A typo like dispatch({ type: "rest" }) is a compile error
  • action.value inside case "setCount" is a guaranteed number — the discriminator narrows the union, exactly like RequestState in Lesson 2

The exhaustiveness win

Add one line to the reducer's switch and TS becomes your maintenance alarm:

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "reset":
      return initialState;
    case "setCount":
      return { ...state, count: action.value };
    default: {
      const _exhaustive: never = action;   // ✅ compiles today
      return state;
    }
  }
}

Here's the trick: if every case is handled, action in the default branch has been narrowed down to never — so assigning it is legal. But add a new variant to the union tomorrow…

type Action =
  | { type: "reset" }
  | { type: "setCount"; value: number }
  | { type: "increment" };        // new!

// ❌ default branch now errors:
// Type '{ type: "increment" }' is not assignable to type 'never'

TS refuses to compile until you handle the new action. Impossible states and forgotten transitions get caught before the code ever runs — this is why production teams prefer reducers for complex state.

A realistic example: shopping cart

interface CartItem {
  id: string;
  name: string;
  qty: number;
}

type CartAction =
  | { type: "add"; item: CartItem }
  | { type: "remove"; id: string }
  | { type: "setQty"; id: string; qty: number }
  | { type: "clear" };

function cartReducer(items: CartItem[], action: CartAction): CartItem[] {
  switch (action.type) {
    case "add":
      return [...items, action.item];
    case "remove":
      return items.filter((i) => i.id !== action.id);
    case "setQty":
      return items.map((i) =>
        i.id === action.id ? { ...i, qty: action.qty } : i
      );
    case "clear":
      return [];
    default: {
      const _exhaustive: never = action;
      return items;
    }
  }
}

Note that the state here is just CartItem[] — state doesn't have to be an object. And each payload field (action.item, action.id) exists only on the action that needs it; there are no optional-everything mega-params.

Pairing with a Provider (Lesson 5 pattern)

Two lessons, two jobs: Lesson 5 answered where shared state lives and how components consume it — a Provider plus guard hooks. This lesson answered how complex transitions get computed — a reducer. They compose directly: keep the Provider's exact Lesson 5 shape, and swap the useState inside it for useReducer. The reducer becomes the engine; nothing else changes.

// Same skeleton as ToastsProvider/AuthProvider — different engine:
export function CartProvider({ children }: { children: React.ReactNode }) {
  const [items, dispatch] = useReducer(cartReducer, []);   // ← was useState

  return (
    <CartDispatchContext value={dispatch}>
      <CartContext value={items}>{children}</CartContext>
    </CartDispatchContext>
  );
}

Why two contexts?

const CartContext = createContext<CartItem[] | null>(null);
const CartDispatchContext = createContext<React.Dispatch<CartAction> | null>(null);

export function useCart(): CartItem[] { /* guard hook */ }
export function useCartDispatch(): React.Dispatch<CartAction> { /* guard hook */ }

Splitting them gives a free performance win, because dispatch is the same stable function on every render:

function CartBadge() {
  const items = useCart();                  // re-renders when items change ✅
  return <span>{items.length}</span>;
}

function AddToCart({ item }: { item: CartItem }) {
  const dispatch = useCartDispatch();       // never re-renders — dispatch never changes ✅
  return <button onClick={() => dispatch({ type: "add", item })}>Add</button>;
}

If you stuffed both into one context value object, adding an item would re-render every consumer — including buttons that can't even see the count.

No new typing concept here. useCartDispatch()'s return type is just React.Dispatch<CartAction> flowing through the same honest-null + guard-hook pattern as AuthContextValue did in Lesson 5.

Recipe: typed useReducer

  1. Define interface State (or an alias like CartItem[])
  2. Define type Action = { type: "..."; ...payload } — discriminated union, one member per transition
  3. Write the reducer outside the component, fully annotated: (state: State, action: Action): State
  4. Switch on action.type; end with the exhaustiveness guard: default: { const _exhaustive: never = action; return state; }
  5. Call useReducer(reducer, initialState) — no explicit generics needed
  6. Growing? Move into a Provider + useX()/useXDispatch() hooks (Lesson 5 pattern)
