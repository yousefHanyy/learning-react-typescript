Prerequisite: Lessons 4 (generics), 6 (utility types)

The problem

Your design system has a beautiful Button. Then design asks for a button that navigates:

<Button>Save</Button>                    <!-- renders <button> -->
<Button href="/docs">Docs</Button>       <!-- should render <a> -->

Wrapping an <a> inside a <button> is invalid HTML and breaks keyboard navigation. The real solution: let the component swap its underlying element via an as prop. You've used this constantly — MUI, Chakra, Radix, styled-components all do it:

<Button as="a" href="/docs">Docs</Button>

This lesson builds the TypeScript machinery that makes that one prop type-safe.

Attempt 1: the union trap

The obvious first draft:

interface ButtonProps {
  as?: "button" | "a";
}

function Button({ as = "button", ...rest }: ButtonProps) {
  const Tag = as;
  return <Tag {...rest} />;
}

It renders fine. But look at what the types allow:

<Button as="a" href="/docs" />   ✅ works by luck — href isn't declared at all... 
                                 wait, it ISN'T. This is a compile error too.

<Button as="button" href="/x" /> ❌ should error... but with no props typed,
                                  everything errors OR nothing checks

The flaw: props are typed independently of the chosen element. Either you whitelist every possible prop (href? | disabled? | target? | type?…) and lose the connection between them, or you accept any. What we actually want is a rule: the legal props are whatever the as element accepts.

The insight: make the element itself a type parameter. When as="a", the props become anchor props; when as="button", button props. One generic, zero manual whitelisting.

The real pattern

import * as React from "react";

type ButtonOwnProps = {           // props specific to YOUR component
  variant?: "primary" | "ghost";
};

type PolymorphicProps<E extends React.ElementType> =
  React.ComponentPropsWithRef<E> & ButtonOwnProps;

export function Button<E extends React.ElementType = "button">({
  variant = "primary",
  as,
  ...rest
}: PolymorphicProps<E>) {
  const Tag = as ?? "button";
  return <Tag {...rest} />;
}

Four pieces, each doing one job:

  1. E extends React.ElementType — constrains the generic to things renderable as JSX: any intrinsic tag ("a", "button"…) and any component type.
  2. = "button" — default type argument mirrors the runtime default. Plain <Button> still type-checks as a button.
  3. React.ComponentPropsWithRef<E> — "all props element E accepts, including ref". For "a": href, target, anchor-typed onClick… For "button": disabled, type…
  4. & ButtonOwnProps — your additions ride along regardless of element.

Now usage proves the payoff:

<Button onClick={save} disabled={!dirty} />        ✅ button props, E inferred "button"
<Button as="a" href="/docs" target="_blank" />     ✅ anchor props
<Button as="a" disabled />                         ❌ Property 'disabled' does not
                                                      exist on anchor props
<Button href="/docs" />                            ❌ default is button — no href

E is inferred from as at the call site — same call-site inference as generic hooks in Lesson 4. The invalid combination is caught before the code runs.

Why not just keyof JSX.IntrinsicElements?

A tighter-looking constraint, but it only allows intrinsic tags. The killer use case dies:

// react-router's Link — a COMPONENT, not an intrinsic tag
<Button as={Link} to="/profile">Profile</Button>   ❌ with keyof JSX.IntrinsicElements
                                                   ✅ with React.ElementType

When as={Link}, E becomes Link's component type and ComponentPropsWithRef<E> resolves to Link's own props — so to is required and typed, while href would be rejected. Your Button instantly composes with any routing library, and each library's props stay exact.

Rule of thumb: keyof JSX.IntrinsicElements when only native tags make sense (e.g. a Text component); React.ElementType for anything users might want to swap.

When your props collide with the element's

Suppose your Button has its own type concept, or wraps a native input whose onChange signature you replace (Lesson 6's TextField). Intersections don't override — clashing members merge badly. Carve them out first:

interface TextFieldOwnProps {
  onChange: (value: string) => void;   // simplified signature, not the event
}

type TextFieldProps<E extends React.ElementType = "input"> =
  Omit<React.ComponentPropsWithRef<E>, "onChange"> & TextFieldOwnProps;

function TextField<E extends React.ElementType = "input">({
  onChange,
  ...rest
}: TextFieldProps<E>) {
  const Tag = E;
  return (
    <Tag
      {...rest}
      onChange={(e) => onChange(e.currentTarget.value)}   // adapt, then hand off
    />
  );
}

Omit<…, "onChange"> removes the native event-based signature so yours wins cleanly — identical move to Lesson 6's wrapper pattern, now generic over the element.

Refs: free in React 19

In older React you needed forwardRef plus a second conditional type just to type the ref. Since 19, ref is an ordinary prop on function components — and notice we used ComponentPropsWithRef<E>, so ref is already in the props type. The {...rest} spread carries it straight through:

const form = useRef<HTMLFormElement>(null);

// E infers "form", ref type-checked as HTMLFormElement
<Button as="form" ref={form} onSubmit={submit}>…</Button>;

No extra code. This is one of the concrete ways React 19 shrinks polymorphic components by roughly a third.

Recipe: polymorphic component

  1. List your own props in an interface (variant, size…).
  2. Type props as Omit<React.ComponentPropsWithRef<E>, keyof OwnProps> & OwnProps — omit any member you replace.
  3. Add as?: E to own props; constrain <E extends React.ElementType = "default-tag"> matching your runtime default.
  4. Destructure as out, spread everything else onto <Tag {...rest} />.
  5. Call sites: never annotate E — let as drive inference.
