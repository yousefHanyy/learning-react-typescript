Prop drilling is why context exists. But the way professional codebases type context has a specific shape — and it always comes wrapped in a custom hook. You've been writing hooks since Lesson 2; now they become the public API.

Basic typing: let the default value infer

useContext gets its type entirely from createContext<T> — you never annotate it at the call site: 

type Theme = "light" | "dark" | "system";

const ThemeContext = createContext<Theme>("system");

// Inside any component — type flows through automatically:
const theme = useContext(ThemeContext);   // theme: Theme

This only works when you have a sensible default. So when does null enter the picture?

The production pattern: | null + a guard hook

import { createContext, useContext, useState, useMemo } from "react";

interface User {
  id: string;
  name: string;
}

interface AuthContextValue {
  user: User | null;
  login: (user: User) => void;
  logout: () => void;
}

// The default IS null — so the type must say so:
const AuthContext = createContext<AuthContextValue | null>(null);

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  const value = useMemo(
    () => ({
      user,
      login: (u: User) => setUser(u),
      logout: () => setUser(null),
    }),
    [user]
  );

  return <AuthContext value={value}>{children}</AuthContext>;
}

export function useAuth(): AuthContextValue {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be used within <AuthProvider>");
  return ctx;
}

Three things are happening here — this is the whole pattern:

  1. The type is honest: AuthContextValue | null, because outside a provider the value genuinely is null. Lying here (createContext<AuthContextValue>(null!)) trades a crash for a silent one.
  2. The hook eliminates null: after the if (!ctx) throw check, TS narrows the return to plain AuthContextValue. Consumers never see null, never write ?.(), never get surprised.
  3. The hook is the API: components call useAuth(). They never import AuthContext itself — many teams don't even export it. If someone uses the hook outside the provider, they get a clear error instead of mysterious null.
React 19: you can now render <AuthContext value={...}> directly instead of <AuthContext.Provider value={...}>. Both work; the shorter form is the modern idiom.
Why useMemo on the value? A fresh object literal every render makes every consumer re-render every time the provider does. Memoizing on [user] means consumers only update when the data actually changes. This matters more as your context grows.

The one rule behind both examples

createContext<T>(defaultValue) has one constraint: the default value must fit inside the type T. Everything else follows from that:

Theme example Auth example
Sensible default? Yes — "system" is a real theme No — there is no fake "logged-in user" we could invent
What we pass as default "system" null ("no session yet")
Type required Theme — already includes "system", nothing changes AuthContextValue | null — must widen, because null isn't an AuthContextValue
Consumer reads a guaranteed Theme, anywhere | null leaks to consumers… unless the hook removes it

So the union in the auth example isn't a special technique — it's just honesty. Outside an AuthProvider, reading the context really does return null, and the type says so. The theme context never has that problem because its default is a genuine value.

The trade-off: you could give auth a fake default object too ({ user: null, login: () => {}, logout: () => {} }) — then no | null needed. But a component using useAuth() outside the provider would silently get that dummy instead of crashing loudly. Real codebases prefer the loud crash.

Custom hooks elsewhere: return types

Most of the time, let inference do the work. Add an explicit return type when you want the contract documented and drift-proof: 

// Inference is fine — hover to see the type:
function useToggle(initial = false) {
  const [on, setOn] = useState(initial);
  return { on, toggle: () => setOn((o) => !o) };
}

// Explicit when it's a shared/public hook:
function useDebouncedValue<T>(value: T, delayMs: number): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const id = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(id);        // refs hold timer IDs — Lesson 3!
  }, [value, delayMs]);

  return debounced;
}

const query = useDebouncedValue(searchText, 300);   // T inferred as string

Note useDebouncedValue<T> — generics work in hooks exactly like components. The debounce above is a real utility you'll find (hand-written or via library) in most production codebases.

Recipe: typed context

  1. Define the value interface — data + actions: interface AuthContextValue { user: User | null; login: ...; logout: ... }
  2. Create with an honest default: createContext<AuthContextValue | null>(null)
  3. Write a Provider component: holds the useState/useReducer, builds the value object inside useMemo, renders <AuthContext value={value}>{children}</AuthContext>
  4. Write a guard hook: const ctx = useContext(AuthContext); if (!ctx) throw new Error(...); return ctx;
  5. Export only the Provider and the hook — never the raw context object
