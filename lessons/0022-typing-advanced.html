The gap after Lesson 13: you can type props, generics, and tests — but real codebases have three gotchas you haven't seen yet: configs that lie about their literals, IDs that are all string but shouldn't mix, and unknown coming from JSON.parse that any would silently accept. Three small tools fix all three.

satisfies — the safe as

You've seen as T in the getJSON boundary (Lesson 10) — one sanctioned lie. Everywhere else, as hides mistakes:

type Theme = { primary: string; secondary: string };

// ❌ as — lies, no error even though "secondry" is a typo:
const theme1 = { primary: "#000", secondry: "#fff" } as Theme;

// ✅ satisfies — checks the shape AND keeps literal types:
const theme2 = { primary: "#000", secondary: "#fff" } satisfies Theme;
type Primary = typeof theme2.primary; // "#000" — literal kept!

// also catches extra keys — useful for config maps:
const routes = {
  home: "/",
  dashboard: "/dashboard",
  typo: "/dashbord", // if Theme expected it, satisfies would flag it
} satisfies Record<string, string>;
Rule: as tells the compiler "trust me" (narrows or widens silently). satisfies says "check me, but don't widen me" — the type is validated, literals stay literal, and autocomplete still works.

When to use: config objects, route maps, theme tokens, any object where you want both validation and literal inference.

as const — literals that stay literal

// without as const — widened, typo in filter compiles:
const ROLES = ["admin", "member", "viewer"];
ROLES.includes("adimn"); // no error — ROLES is string[]

// with as const — readonly tuple of literals:
const ROLES2 = ["admin", "member", "viewer"] as const;
type Role = typeof ROLES2[number]; // "admin" | "member" | "viewer"
ROLES2.includes("adimn"); // ❌ compile error — "adimn" not assignable

Same move for objects — makes every property readonly and literal:

const CONFIG = {
  apiUrl: "https://api.example.com",
  retries: 3,
} as const;
CONFIG.retries = 5; // ❌ Cannot assign to 'retries' because it is a read-only property

Gotcha: as const makes the whole thing deeply readonly. If a library expects string[] (mutable), pass [...ROLES2] or type the param as readonly string[].

Branded types — stop mixing IDs

Every ID is string — but UserId and PostId should never mix. TypeScript is structural, so without help they're compatible:

function getUser(id: string) {}
function getPost(id: string) {}
getUser("post_123"); // compiles — wrong!

// Branded (nominal) IDs — same runtime, different types:
type UserId = string & { readonly __brand: "UserId" };
type PostId = string & { readonly __brand: "PostId" };

function getUser2(id: UserId) {}
function getPost2(id: PostId) {}

declare const uid: UserId;
declare const pid: PostId;
getUser2(pid); // ❌ Type 'PostId' is not assignable to 'UserId'
getUser2(uid); // ✅

// helpers — one place where the cast lives:
function toUserId(raw: string): UserId { return raw as UserId; }
function toPostId(raw: string): PostId { return raw as PostId; }
Real-world use: design systems and backends brand UserId, OrderId, Currency strings — catches copy-paste bugs where you pass the wrong ID to an API. Zero runtime cost.

Narrowing unknown — the honest any

any disables checks. unknown forces you to narrow before use — exactly what you want at boundaries (JSON.parse, catch (e), postMessage):

// ❌ any — typo compiles, crashes at runtime:
const data: any = JSON.parse(raw);
data.emial; // no error — any

// ✅ unknown — must narrow before access:
const data2: unknown = JSON.parse(raw);
if (typeof data2 === "object" && data2 !== null && "email" in data2
    && typeof (data2 as any).email === "string") {
  console.log((data2 as { email: string }).email);
}

// in practice — zod does the narrowing for you (Lesson 11):
const parsed = schema.safeParse(JSON.parse(raw)); // unknown → validated Values
if (parsed.success) {
  parsed.data.email; // ✅ typed, validated
}

The line: catch (e: unknown) — not any — then if (e instanceof Error) e.message. Same pattern as FetchState narrowing from Lesson 10.

never's job: the exhaustiveness guard (const _exhaustive: never = action from Lesson 7) and impossible branches — if a value is never, that code is unreachable.

Recipe: advanced patterns at work

  1. Config/route maps: const x = { ... } satisfies Expected — validates without widening.
  2. Literal unions from arrays: const ROLES = [...] as const; type Role = typeof ROLES[number].
  3. IDs that shouldn't mix: type UserId = string & { readonly __brand: "UserId" } + toUserId(raw) helper.
  4. Boundaries: type as unknown first (JSON.parse, catch (e)), narrow with typeof/instanceof or zod.safeParse.
  5. Need an exhaustive check: const _exhaustive: never = action in default.
