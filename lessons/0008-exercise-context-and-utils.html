Challenge 1 · Lesson 5

Build a typed ToastContext

Objective: write the full production context pattern from memory.

Create a toast notification context:
  • Toast: { id: number; message: string }
  • Context value: the toast list + a showToast(message: string) action
  • A ToastsProvider holding the state
  • A useToasts() hook that consumers call — it must never hand out null
Rules: honest default on createContext, export only the Provider and the hook.

Solution

import { createContext, useContext, useState, useMemo } from "react";

interface Toast {
  id: number;
  message: string;
}

interface ToastsContextValue {
  toasts: Toast[];
  showToast: (message: string) => void;
}

// Default IS null — the type says so:
const ToastsContext = createContext<ToastsContextValue | null>(null);

export function ToastsProvider({ children }: { children: React.ReactNode }) {
  const [toasts, setToasts] = useState<Toast[]>([]);

  const value = useMemo(
    () => ({
      toasts,
      showToast: (message: string) =>
        setToasts((prev) => [...prev, { id: Date.now(), message }]),
    }),
    [toasts]
  );

  return <ToastsContext value={value}>{children}</ToastsContext>;
}

export function useToasts(): ToastsContextValue {
  const ctx = useContext(ToastsContext);
  if (!ctx) throw new Error("useToasts must be used within <ToastsProvider>");
  return ctx;
}
Challenge 2 · Lesson 5

Debug the settings page

Objective: spot two problems with raw context consumption.

This component has a compile error and breaks a convention from Lesson 5. Find both and fix:

function SettingsMenu() {
  const { user, logout } = useContext(AuthContext);   // ❌

  if (!user) return <p>Not logged in</p>;
  return <button onClick={logout}>Log out {user.name}</button>;
}

Solution

function SettingsMenu() {
  const { user, logout } = useAuth();   // ✅ the hook is the API

  if (!user) return <p>Not logged in</p>;
  return <button onClick={logout}>Log out {user.name}</button>;
}

The two problems:

  1. Compile error: AuthContext holds AuthContextValue | null, so TS refuses the destructure — you can't pull properties off a possibly-null value.
  2. Convention break: components shouldn't touch the raw context object. The guard hook exists precisely to remove null once, centrally. Note that user: User | null stays in the type — being logged out is real data — but the context value itself can no longer be null.
Challenge 3 · Lesson 6

Derive four types from User

Objective: reshape one source type with utilities — no redeclaring fields.

Given: 
type Role = "admin" | "editor" | "viewer";

interface User {
  id: string;
  name: string;
  email: string;
  password: string;
  createdAt: string;
  role: Role;
}
Derive, using only utility types:
  1. PublicUser — everything except password
  2. UserDraft — what a signup form submits: all fields except id and createdAt
  3. UserPatch — any subset of UserDraft fields, for updates
  4. permissions — an object that must have a string[] entry for every possible Role

Solution

type PublicUser = Omit<User, "password">;

type UserDraft = Omit<User, "id" | "createdAt">;

type UserPatch = Partial<UserDraft>;

const permissions: Record<Role, string[]> = {
  admin:  ["read", "write", "delete"],
  editor: ["read", "write"],
  viewer: ["read"],
};

Note what you get for free: add a field to User tomorrow and every derived type updates automatically. Add a new Role member and TS immediately errors that permissions is incomplete — that's Record's completeness check.

Challenge 4 · Lesson 6

Wrap a native input

Objective: the design-system pattern — extend native props, replace one.

Build a PasswordInput for a design system:
  • Accepts every prop a normal <input> accepts (placeholder, disabled, aria-*, …)
  • Except onChange — yours takes the plain string: onChange: (value: string) => void
  • And except type — the component always renders type="password" internally
  • No manual redeclaration of native props; no any

Solution

interface PasswordInputProps
  extends Omit<React.ComponentPropsWithoutRef<"input">, "onChange" | "type"> {
  onChange: (value: string) => void;
}

function PasswordInput({ onChange, ...rest }: PasswordInputProps) {
  return (
    <input
      {...rest}
      type="password"
      onChange={(e) => onChange(e.currentTarget.value)}
    />
  );
}

// Usage — native props still work, fully typed:
<PasswordInput
  placeholder="Enter password"
  autoComplete="new-password"
  disabled={loading}
  onChange={(value) => setPassword(value)}
/>

The key move: Omit<..., "onChange" | "type"> removes only the two props you're replacing/locking, then your own declarations take over. Everything else flows through via {...rest}.

Stretch · Lessons 4 + 5

Generic useLocalStorageState

Objective: combine generics, hook structure, and tuple typing.

Write a generic useLocalStorageState<T>(key, initial) hook:
  • Reads the stored value lazily on first render (not on every render)
  • Persists every change back to localStorage
  • Returns [value, setValue] as a proper tuple — not an array of union type
You'll need Lesson 4 generics, Lesson 5 hook structure, lazy useState initialization, and an explicit tuple return type.

Solution

import { useEffect, useState } from "react";

function useLocalStorageState<T>(
  key: string,
  initial: T
): [T, (value: T) => void] {
  // Lazy initializer — runs once, not on every render:
  const [value, setValue] = useState<T>(() => {
    const stored = localStorage.getItem(key);
    return stored ? (JSON.parse(stored) as T) : initial;
  });

  useEffect(() => {
    localStorage.setItem(key, JSON.stringify(value));
  }, [key, value]);

  return [value, setValue] as const;
}

// Usage — T inferred from initial:
const [name, setName] = useLocalStorageState("username", "Ada");
const [cart, setCart] = useLocalStorageState<Item[]>("cart", []);

The three teaching points:

  1. Lazy init: passing a function to useState means localStorage.getItem runs only on the first render.
  2. The tuple return: without it, TS infers (T | ((value: T) => void))[] — destructuring would give both elements that union type. The explicit annotation [T, (value: T) => void] (or as const) keeps value and setValue distinct.
  3. Honest caveat: JSON.parse(...) as T is an assertion — stored data could be stale or tampered. Production versions validate on read (or use a library like use-local-storage-state). Assertions are acceptable at trust boundaries you control — just know that's what this is.
