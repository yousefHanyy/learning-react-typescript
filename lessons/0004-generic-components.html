Generic Components

~7 min · Builds on: Lesson 2 (generics) · Glossary

← Lesson 3: Refs Next: Exercise 1

You already understand generics from useState<T>. Now the same idea moves to components: a component whose props type depends on a type you supply at the call site.

The core pattern: List<T>

interface ListProps<T> {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}

function List<T>({ items, renderItem }: ListProps<T>) {
  return <ul>{items.map(renderItem)}</ul>;
}

// TypeScript infers T from what you pass:
<List
  items={users}                // T = User (inferred, no annotation needed)
  renderItem={(u) => <li>{u.name}</li>}
/>

Pass users (an array of User) and T becomes User automatically — renderItem's u is typed as User, with full autocomplete and no any.

This is the single most common generic component in production — lists, dropdowns, tables, virtualized grids. Once you see it, you'll notice it everywhere.

Constraining T with extends

If you need T to guarantee certain properties, constrain it. This lets you read item.id without erroring:

interface Identifiable { id: string | number; }

function List<T extends Identifiable>({ items }: { items: T[] }) {
  return (
    <ul>
      {items.map((item) => <li key={item.id}>{item.id}</li>)}
    </ul>
  );
}

<List items={users} />            // ✅ users have an id
<List items={[1, 2, 3]} />        // ❌ numbers have no id

A production example: Select

Generic components really shine for "give me an item, get back its value" components:

interface SelectProps<T> {
  options: T[];
  getValue: (option: T) => string;
  onSelect: (value: string) => void;
}

function Select<T>({ options, getValue, onSelect }: SelectProps<T>) {
  return (
    <select onChange={(e) => onSelect(e.currentTarget.value)}>
      {options.map((opt) => (
        <option key={getValue(opt)} value={getValue(opt)}>
          {String(opt)}
        </option>
      ))}
    </select>
  );
}

// Works with users, products, countries — any type:
<Select
  options={countries}
  getValue={(c) => c.code}
  onSelect={(code) => setSelectedCode(code)}
/>
Gotcha: in a .tsx file, a generic arrow function needs a trailing comma or extends — otherwise JSX confuses <T> with a tag: const List = <T,>({ items }: { items: T[] }) => .... Using a function declaration (as above) sidesteps this entirely.

When to reach for a generic — and when not

A generic has exactly one job: preserve a type the caller controls across two or more positions in a signature. Nothing to link → no generic. That's the entire decision.

The only two legitimate jobs:

// Job 1: CORRELATION — the same T appears in multiple slots and must stay in sync
function List<T>({ items, renderItem }: {
  items: T[];                              // whatever array you pass...
  renderItem: (item: T) => React.ReactNode;
})                                         // ...your callback receives ITS elements

// Job 2: CALLER KNOWS BEST — the implementation genuinely cannot know,
// so the caller declares (Lesson 10's wrapper lives here too)
const users = await getJSON<User[]>(url);   // T appears once — in the return

Three smell tests, in order:

  1. Duplication test: without the generic, would you copy-paste the whole function per type? No → you probably don't need it.
  2. Single-use test: count the Ts. One occurrence in the params, nowhere else? Delete the generic — when a constraint does all the work, the constraint IS the type.
  3. Rename test: replace every T with "whateverTheCallerSent". Does the signature still promise something true and useful? If it reads as ceremony, it is ceremony.
// ❌ generic theater — T links nothing; the constraint did everything
function getTotal<T extends CartItem[]>(items: T): number

// ✅ the honest version — identical power, zero ceremony
function getTotal(items: CartItem[]): number

// ✅ generic earns its keep — input and output are THE SAME caller type
function useDebouncedValue<T>(value: T, delay: number): T

Union or generic? A closed set of shapes you know today → union ("idle" | "loading"). Open-ended, caller-owned shapes → generic. And the workflow that prevents premature generics altogether: write it concrete first. The moment a second type arrives and you feel the copy-paste reflex — that exact moment is when you lift it into a generic. Concrete→generic refactoring is cheap; unwriting an unnecessary generic is morale tax.

Quick Check

When you pass items={users} to List<T>, how does TS determine T?

How do you require T to have a specific property?

Recipe: generic component

  1. Put T in the props interface where values flow through: interface ListProps<T> { items: T[] }
  2. Declare it on a function statement: function List<T>({...}: ListProps<T>) { ... } (avoids the .tsx arrow gotcha)
  3. Need guaranteed properties? Constrain: <T extends Identifiable>
  4. At the call site, pass real data — T is inferred, never written manually
