2. Events

The handler types you'll actually use

// React 19 (@types/react ≥ 19): SubmitEvent — NOT React.FormEvent
// React.FormEvent is DEPRECATED as a submit handler type
const handleSubmit = (e: React.SubmitEvent<HTMLFormElement>) => {
  e.preventDefault();
};

const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
  console.log(e.currentTarget.value);   // currentTarget: typed element
};                                      // target: EventTarget (untyped!) — prefer currentTarget

// Handler PROP on your own component:
interface SearchInputProps {
  onChange: (value: string) => void;    // usually simplify — pass the value,
}                                       // not the event (see wrapping section)

Gotcha (cost us a correction once): older tutorials say React.FormEvent for onSubmit — deprecated in @types/react v19 (verified against 19.2.10). Use SubmitEvent<HTMLFormElement>.

3. useState

Inference vs explicit generic

const [name, setName] = useState("");            // infers "" → string
const [user, setUser] = useState(null);          // ⚠ infers null ONLY —
const [user, setUser] = useState<User | null>(null);  // fix: explicit generic
const [items, setItems] = useState<Item[]>([]);       // [] alone infers never[]

Rule: annotate when the initial value can't tell the whole story (empty array, null that will later hold an object).

Union state — the workhorse pattern

type FetchState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: User[] }
  | { status: "error"; message: string };

const [state, setState] = useState<FetchState>({ status: "idle" });

// rendering narrows automatically:
if (state.status === "success") {
  state.data.map(...)      // ✅ data only exists here — TS knows
}

Gotcha: never model this as one interface with optional fields ({ data?: User[]; error?: string }) — you lose the guarantee they can't coexist.

4. Refs (both kinds)

DOM refs — the honest nullable

const inputRef = useRef<HTMLInputElement>(null);
// inputRef.current: HTMLInputElement | null
// null until AFTER first render/mount — that's why it's in the type

useEffect(() => {
  inputRef.current?.focus();     // optional chain or guard — never assume
}, []);

Value refs — mutable box, NO re-render

const renderCount = useRef(0);
renderCount.current += 1;        // changes silently, no re-render, ever

Gotcha (the counter trap): mutating a ref does not update UI. If the screen should change when the value changes, it's useState, full stop. Refs are for values React doesn't need to react to (timer ids, previous values, DOM nodes).

Refs to custom components (React 19)

<FancyInput ref={inputRef} />    // just works — ref is a normal prop now

// typing YOUR component's ref prop:
interface FancyInputProps {
  ref?: React.Ref<HTMLInputElement>;   // Ref accepts object refs AND callback refs
}

Gotcha: don't type it RefObject<T> — that rejects callback refs like ref={(node) => …}. React.Ref<T> accepts both. forwardRef is legacy — unnecessary since 19.

Sources: Lesson 3 · DOM refs, Lesson 3 · value refs, Lesson 3 · ref-as-prop

5. Generic components & hooks

Component pattern

function List<T>({ items, renderItem }: {
  items: T[];
  renderItem: (item: T) => React.ReactNode;
}) {
  return <ul>{items.map(renderItem)}</ul>;
}

// T inferred from the CALL SITE — never annotate manually:
<List items={users} renderItem={(u) => u.name} />   // T = User

Constraints with extends

function Select<T extends { id: string; label: string }>(props: {
  options: T[];
  value: T["id"];                 // keyed access keeps it generic
  onChange: (id: string) => void;
}) {...}

Gotcha: without a constraint, T allows anything — you can't access item.id inside. The extends clause is what buys property access.

Render props vs custom hooks

Custom hookRender prop
Reuseslogic (state/effects)behavior wrapped around YOUR JSX
Choose whenyou just need the data/functionsa component must control mounting/rendering around your content
ExampleuseDebouncedValue(text, 300)<Virtualizer items={x}>{(v) => …}</Virtualizer>

Modern default: reach for a hook first; render props survive where the wrapper genuinely owns DOM/lifecycle around children.

When to reach for a generic — the decision test

One job only: preserve a caller-controlled type across positions in a signature. Two legit uses: correlation (same T in 2+ slots: items: T[] + renderItem: (i: T) => …) and caller-declared returns (getJSON<User[]> — implementation can't know, T appears once in return). Everything else → concrete type.

  • Duplication test: without the generic, would you copy-paste per type? No → skip it.
  • Single-use test: T appears once in params and nowhere else? Delete the generic — the constraint alone was the type: <T extends CartItem[]>(items: T) ≡ (items: CartItem[]).
  • Closed vs open: known small set of shapes → union. Caller-owned open shapes → generic.
  • Workflow: write concrete first; generalize exactly when a second type arrives.

6. Context — the production pattern

Honest null + guard hook (the standard)

interface AuthContextValue {
  user: User;
  signIn: (email: string) => Promise<void>;
}

const AuthContext = createContext<AuthContextValue | null>(null);
//                                     ^^^^^^ WHY: outside a provider the
//                                     stored value IS null — honest types only

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);

  const value = useMemo(() => ({
    user,
    signIn: async (email: string) => { /* ... */ },
  }), [user]);
  // ^ GOTCHA: without useMemo the value object is new every render →
  //   EVERY consumer re-renders every time, context memoization defeated

  return (
    <AuthContext value={value}>    {/* React 19: no ".Provider" needed */}
      {children}
    </AuthContext>
  );
}

export function useAuth(): AuthContextValue {
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be used within <AuthProvider>");
  return ctx;                       // narrowed: AuthContextValue — null gone
}

Why the throw isn't just for debugging: the guard is also the narrowing mechanism — after it, TS eliminates null from the return type. Consumers never write a null check.

When a non-null default is fine instead: values that legitimately exist before any provider — e.g. theme constants (createContext("light")). The rule: does a sensible standalone default exist? Yes → use it. No → honest null + guard hook.

Encapsulation rule: components consume useAuth(), NEVER raw useContext(AuthContext) — keep the context object module-private, export only Provider + hook.

Sources: Lesson 5 · guard hook pattern, Lesson 5 · the honesty rule

Split contexts: state vs dispatch (performance)

const CartStateContext = createContext<CartState | null>(null);
const CartDispatchContext = createContext<React.Dispatch<CartAction> | null>(null);

// Provider nests both (see useReducer section for the reducer)
// Consumers pick their poison:
const cart = useCart();              // re-renders on every cart change — needs values
const dispatch = useCartDispatch();  // STABLE across renders → component using ONLY
                                    // this never re-renders from cart updates

Why bother: dispatch is created once by useReducer and never changes. A button that only dispatches has zero reason to re-render when the cart contents change — but it would, if both lived in one context.

8. Wrapping native elements

The ComponentProps family

type ButtonProps = React.ComponentProps<"button">;             // native tag
type LinkProps = React.ComponentProps<typeof RouterLink>;      // another component
type InputProps = React.ComponentPropsWithRef<"input">;        // incl. ref
type PlainInputProps = React.ComponentPropsWithoutRef<"input">;// ref excluded

Replacing a prop signature (the TextField move)

// GOAL: consumers pass a plain string onChange — hide the event machinery.
// You're not "adding" onChange, you're REPLACING the native one.

interface TextFieldOwnProps {
  onChange: (value: string) => void;         // simplified contract
}

type TextFieldProps =
  Omit<React.ComponentPropsWithRef<"input">, "onChange">   // carve out FIRST
  & TextFieldOwnProps;                                      // then intersect

function TextField({ onChange, ...rest }: TextFieldProps) {
  return (
    <input
      {...rest}
      onChange={(e) => onChange(e.currentTarget.value)}     // adapt & delegate
    />
  );
}

Why Omit before intersecting: an intersection of clashing members produces an impossible type (both signatures required), NOT an override. Omit removes the native member so yours wins cleanly. This exact move scales up into polymorphic components.

Other legit replace-cases: locking type="password" (Omit "type"), forcing value/defaultValue semantics, narrowing onChange to controlled-only.

Sources: Lesson 6 · ComponentProps, Lesson 9 · collisions

9. useReducer

The trio — annotate the reducer, infer everything else

interface FiltersState {
  query: string;
  maxPrice: number;
  inStockOnly: boolean;
}

type FiltersAction =
  | { type: "setQuery"; value: string }      // payload fields exist ONLY
  | { type: "setMaxPrice"; value: number }   // where they're needed —
  | { type: "toggleInStock" }                // toggleInStock has NO value field,
  | { type: "reset" };                       // so TS rejects stray payloads

const initialFilters: FiltersState = { query: "", maxPrice: 100, inStockOnly: false };

function filtersReducer(state: FiltersState, action: FiltersAction): FiltersState {
  switch (action.type) {
    case "setQuery":     return { ...state, query: action.value };
    case "toggleInStock": return { ...state, inStockOnly: !state.inStockOnly };
    // ...
    default: {
      const _exhaustive: never = action;    // the exhaustiveness guard
      return state;
    }
  }
}

// ONE line wires it — State, Action, dispatch ALL inferred:
const [filters, dispatch] = useReducer(filtersReducer, initialFilters);
// dispatch: React.Dispatch<FiltersAction>  (typed for free)

Don't write useReducer<FiltersState, FiltersAction> — redundant; annotating the reducer parameter is the single source of truth.

Exhaustiveness guard — the mechanics (memorize this)

  1. All cases handled → narrowing eliminated every variant → action in default is never → assignment legal → compiles.
  2. Add a variant, forget the case → that variant SURVIVES narrowing into default → assigning it to never fails → error appears IN the default branch: Type '{ type: "clear"; }' is not assignable to type 'never'.
  3. The error location IS your TODO list — handle the missing case, compile passes again.

Gotcha: a default that just returns state WITHOUT the never-guard compiles silently forever — you lose all protection. The guard line is the whole point.

FormData.get — always narrow (no exceptions)

async function signUp(formData: FormData): Promise<void> {
  const name = formData.get("name");
  // type: FormDataEntryValue | null   ← ALWAYS, even for existing inputs
  if (typeof name !== "string" || name.trim() === "") return;

  const email = formData.get("email");
  if (typeof email !== "string" || !email.includes("@")) return;

  await api.createUser({ name, email });   // both narrowed to string
}

Why typeof, not truthiness: "0" and " " are truthy strings; File values pass truthiness too. typeof x !== "string" is the only check that's exactly right.

useActionState — the four details people forget

const [state, submitAction, isPending] =
  useActionState(subscribe, { error: null });
//  ^state     ^action      ^pending — slots in THIS order

async function subscribe(
  prevState: SubscribeState,      // ← state FIRST — the argument flip;
  formData: FormData              //   bare action-prop handlers take formData only
): Promise<SubscribeState> {
  // EVERY code path returns a fresh state object —
  // returning { error: null } on success is what clears old errors
}

Gotchas: (1) state type comes from the INITIAL VALUE — no generic annotation needed; (2) forget the prevState param and TS flags the mismatch immediately — trust it.

11. Polymorphic components (as prop)

import * as React from "react";

interface ButtonOwnProps<E extends React.ElementType> {
  variant?: "primary" | "ghost";
  as?: E;                                     // the swap handle, typed by E
}

type PolymorphicProps<E extends React.ElementType> =
  React.ComponentPropsWithRef<E> & ButtonOwnProps<E>;

export function Button<E extends React.ElementType = "button">({
  variant = "primary",
  as,
  ...rest                                   // ref rides in here (React 19)
}: PolymorphicProps<E>) {
  const Tag = as ?? "button";
  return <Tag {...rest} />;
}
<Button disabled={!dirty} />                ✅ E = "button"
<Button as="a" href="/docs" target="_blank" /> ✅ E = "a" — anchor props
<Button as="a" disabled />                  ❌ compile error: anchors have no disabled
<Button as={RouterLink} to="/me" />         ✅ component targets — ElementType
                                           required (keyof JSX.IntrinsicElements
                                           would reject Link!)

Constraint rule of thumb: React.ElementType when callers might swap in components (routers, design systems). keyof JSX.IntrinsicElements only when native tags are the whole point.

Refs: free — ComponentPropsWithRef<E> puts ref in the spread; React 19 forwards it through function components natively. No forwardRef.

Own-prop collisions: anything you redefine gets Omit'd from the element props BEFORE intersection (see §8) — same move, generic edition.

12. Typing data fetching

The boundary problem

const users = await (await fetch(url)).json();
//    ^ any — json() cannot know your schema; every typo compiles from here on

All trust in external data is established ONCE at a wrapper, or validated at runtime (zod — what production teams adopt when APIs misbehave). Types never check runtime shapes; only assertions and validators do.

The wrapper — both jobs it does

async function getJSON<T>(url: string): Promise<T> {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`Request failed: ${res.status} ${res.statusText}`);
  return (await res.json()) as T;
}
  • res.ok check: fetch does NOT throw on 404/500 — resolves happily. Without this, failures masquerade as data.
  • as T: the one sanctioned lie — "I verified the server sends T." Keep ALL such assertions in this one layer so contract fixes stay one-file.

The state machine + hook

type FetchState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }     // data exists HERE and ONLY here
  | { status: "error"; message: string };

function useFetch<T>(url: string): FetchState<T> {
  const [state, setState] = useState<FetchState<T>>({ status: "idle" });
  useEffect(() => {
    let cancelled = false;
    setState({ status: "loading" });
    getJSON<T>(url)
      .then((d) => !cancelled && setState({ status: "success", data: d }))
      .catch((e) => !cancelled && setState({ status: "error", message: String(e) }));
    return () => { cancelled = true; };   // stale-response guard
  }, [url]);
  return state;
}

// consumption — narrowing makes crashes unrepresentable:
switch (state.status) {
  case "success":
    state.data.map(...)   // ✅ no ?., no ! — data provably present
}

Why not booleans: { isLoading, data?, error? } allows illegal combos (loading AND errored AND data). The union makes them unrepresentable — precedence logic compiles away entirely.

API shape rule: type fields exactly as sent — no defensive optionals; genuine API inconsistency belongs to runtime validation, not weakened types.

13. Typed forms — Zod + React Hook Form

Schema is the type

const schema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
  role: z.enum(["admin", "member"]),
});
type Values = z.infer<typeof schema>;   // ONE source of truth — never hand-write the interface
// z.input<typeof schema> vs z.output — only differ when transforms exist

Wiring

import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";

const { register, handleSubmit, control, formState: { errors } } =
  useForm<Values>({
    resolver: zodResolver(schema),
    defaultValues: { name: "", email: "", role: "member" },
  });

// submit receives validated Values — no FormData narrowing:
const onSubmit = (data: Values) => { /* ... */ };
<form onSubmit={handleSubmit(onSubmit)}>
  • register("name") is Path<Values> — typo = compile error.
  • errors is FieldErrors<Values> — errors.email?.message is string | undefined.

register vs Controller

Use whenExample
register("field")native <input>/<select><input {...register("email")} />
<Controller name="field" control={control} render={({ field }) => …} />controlled component (value/onChange props)DatePicker, MUI Select

Controller typing — how field.value becomes "admin" | "member": Controller is generic in TFieldValues (from control: Control<Values>) and TName extends FieldPath<TFieldValues> (from name="role"). They infer to ControllerRenderProps<Values, "role"> where value is FieldPathValue<Values, "role">. Destructure only what you need: render={({ field }) => …} for minimal, ({ field, fieldState, formState }) for full. render IS the render-prop survivor from Lesson 4 — the wrapper must own field lifecycle but can't know your JSX, so it calls your function with the typed field object. Hook alternative: useController({ name, control }) returns the same { field, fieldState }.

Resolver is a gate: with zodResolver(schema), handleSubmit(onSubmit) runs schema.safeParse(values) before onSubmit. Fail → errors populated, callback never called. Pass → callback receives the validated/coerced/transformed output. That's why data: Values needs no FormData.get checks. Default mode is onSubmit; add mode: "onChange" to validate while typing.

fieldState vs formState — what to read where: fieldState is per-field (error?: FieldError, invalid, isDirty, isTouched, isValidating) — use inside Controller render for inline messages/borders. formState is whole-form (errors, isDirty, isValid, isSubmitting, isSubmitted, isSubmitSuccessful, dirtyFields, touchedFields, submitCount) — use outside fields. Disable submit at the form level: const { formState: { isSubmitting } } = useForm(...) then <button disabled={isSubmitting}> (destructure — Proxy subscription). Don't put form-wide logic inside a single field's render.

Numbers and transforms

// number inputs are strings in the DOM — coerce in zod (preferred):
z.coerce.number().min(18)
// or: register("age", { valueAsNumber: true }) — pick one, not both

// when a field transforms (string → string[]), handleSubmit's type diverges:
type Input = z.input<typeof schema>;
type Output = z.output<typeof schema>;
useForm<Input, unknown, Output>({ resolver: zodResolver(schema) });

14. Performance & memo

// memo — type inferred from component, no special generic needed:
const Row = memo(function Row({ user, onSelect }: RowProps) { ... });

// useMemo / useCallback — inferred from factory:
const visible = useMemo(() => users.filter(u => u.role === filter), [users, filter]);
const handleSelect = useCallback((id: string) => setSelected(id), []);
const handleChange = useCallback<React.ChangeEventHandler<HTMLInputElement>>(
  e => setValue(e.currentTarget.value), []
);

When memo helps: profiler shows slowness AND props are stable (objects via useMemo, functions via useCallback) AND child is expensive/many. Otherwise you pay comparison cost and still render — new object/function each render defeats shallow compare.

Junior rule: don't memo until measured. Prefer correct deps and primitives over memo.

15. Testing typed components You flagged this as harder — take 13a first

Quick reminder — vi.fn() is jasmine.createSpy() renamed: creates a standalone fake function with empty call history. Call it (onSave(42)), then assert: expect(onSave).toHaveBeenCalled() / toHaveBeenCalledWith(42) / toHaveBeenCalledTimes(2). Clear with onSave.mockClear() (was spy.calls.reset()). Add a type when you want the compiler to check args: vi.fn<(n: number) => void>().

When to use which — the one-line rule: vi.fn() when you create the function (you own it, you pass it in as a prop). vi.spyOn(obj, "method") when you watch/mock a method that already lives on an object/module (you don't own it, you intercept it).

vi.fn()vi.spyOn(obj, "method")
You docreate a new fakewrap an existing method with a fake
Typed?opt-in: vi.fn<(n: number) => void>()auto-typed from the real method — no generic needed
Restore?mockClear() (clear history)mockRestore() (put real method back) or mockClear()

Realistic vi.fn() — testing a prop callback you provide:

// Counter calls onSave when clicked — you supply the spy:
function Counter({ onSave }: { onSave: (n: number) => void }) {
  return <button onClick={() => onSave(42)}>Save</button>;
}

test("calls onSave with 42", async () => {
  const onSave = vi.fn(); // you created it — no object to spy on
  render(<Counter onSave={onSave} />);
  await userEvent.setup().click(screen.getByRole("button", { name: /save/i }));
  expect(onSave).toHaveBeenCalledWith(42);
  expect(onSave).toHaveBeenCalledTimes(1);
});

Realistic vi.spyOn — intercepting an existing module/object:

// api.ts — real code that hits the network (you don't want it in tests):
export const api = {
  getJSON: (url: string) => fetch(url).then(r => r.json()),
  saveUser: (u: User) => fetch("/api/users", { method: "POST", body: JSON.stringify(u) }),
};

// UserList.tsx calls api.getJSON internally — you intercept it:
import * as api from "../api";

test("shows users from api", async () => {
  // wrap the REAL getJSON — now it's a spy, and we fake its resolved value:
  const spy = vi.spyOn(api, "getJSON").mockResolvedValue([
    { id: "1", name: "Ada" },
  ]);

  render(<UserList />);
  expect(await screen.findByText("Ada")).toBeInTheDocument();
  expect(spy).toHaveBeenCalledWith("/api/users"); // automatically typed: (url: string)

  spy.mockRestore(); // put the real getJSON back — other tests aren't affected
});

test("handles save failure", async () => {
  // you can also make it reject to test error paths:
  vi.spyOn(api, "saveUser").mockRejectedValue(new Error("Network error"));
  render(<UserForm />);
  await userEvent.setup().click(screen.getByRole("button", { name: /save/i }));
  expect(await screen.findByText(/network error/i)).toBeInTheDocument();
  vi.restoreAllMocks();
});

Rule of thumb: need to provide a function? vi.fn(). Need to observe/replace a function that already exists somewhere else? vi.spyOn. When in doubt, ask: "did I create this function for the test, or did it already exist on an object before the test?"

"Wrap with the real provider" — what is real? The real provider is the actual <AuthProvider> component from your auth.tsx file — the one your App.tsx uses — with its real useState/useMemo logic inside. Wrapping with it runs that logic, so if the provider is broken the test fails.

// auth.tsx — the real file:
const AuthContext = createContext<AuthContextValue | null>(null); // private — not exported

export function AuthProvider({ children }: { children: React.ReactNode }) {
  const [user, setUser] = useState<User | null>(null);
  const value = useMemo(() => ({ user, signIn, signOut }), [user]);
  return <AuthContext value={value}>{children}</AuthContext>;
}
export function useAuth() { // components call this — it throws if outside a provider
  const ctx = useContext(AuthContext);
  if (!ctx) throw new Error("useAuth must be within <AuthProvider>");
  return ctx;
}

// ✅ Real wrapper — test the integration that actually ships:
import { AuthProvider } from "../auth";
render(<Profile />, { wrapper: ({ children }) => <AuthProvider>{children}</AuthProvider> });
expect(screen.getByText(/welcome/i)).toBeInTheDocument();

// hooks too — same wrapper trick:
const { result } = renderHook(() => useAuth(), { wrapper: ({ children }) => <AuthProvider>{children}</AuthProvider> });

Not real — hand-made fakes that skip the provider:

// ❌ faking the hook — bypasses provider entirely, won't catch a broken provider:
vi.mock("../auth", () => ({ useAuth: () => ({ user: fakeUser, signIn: vi.fn() }) }));

// ❌ hand-crafting the raw context value — also skips AuthProvider's logic/memmoization:
<AuthContext.Provider value={{ user: fakeUser, signIn: vi.fn() }}>
  <Profile />
</AuthContext.Provider>

Both compile but drift when AuthContextValue gains a field (e.g. signOut) — the fake stays silent while the real app breaks. Need a specific state (e.g. "logged-in as admin")? Give the real provider a test prop: <AuthProvider initialUser={admin}> — still the real component, just seeded. That's Lesson 13b's rule: real wrapper by default, mock the hook only as an escape hatch.

"Mock the boundary, not fetch" — what boundary? The boundary is the one file you own that touches the outside world — in this course, api.ts's getJSON<T> wrapper from Lesson 10 (res.ok check + single as T). fetch is the raw browser API — global, untyped, requires you to fake Response objects.

// api.ts — the boundary you own (ONE place where as T lives):
export async function getJSON<T>(url: string): Promise<T> {
  const res = await fetch(url);
  if (!res.ok) throw new Error(`Failed: ${res.status}`);
  return (await res.json()) as T;
}

// ❌ mocking fetch — you now fake Response, headers, .json(), ok, etc.:
vi.spyOn(globalThis, "fetch").mockResolvedValue(
  new Response(JSON.stringify([{ id: "1" }]), { status: 200 })
  // easy to get wrong, untyped, leaks to other tests
);

// ✅ mocking the boundary — typed, minimal, local:
vi.mock("../api", () => ({
  getJSON: vi.fn(async () => [{ id: "1", name: "Ada" }]),
}));
// or per-test spy (same boundary, more control):
import * as api from "../api";
const spy = vi.spyOn(api, "getJSON").mockResolvedValue([{ id: "1", name: "Ada" }]);
render(<UserList />); // UserList calls getJSON internally — you intercepted the boundary
expect(spy).toHaveBeenCalledWith("/api/users");
spy.mockRestore();

// still test errors — just make the boundary reject:
vi.spyOn(api, "getJSON").mockRejectedValue(new Error("Network error"));
render(<UserList />);
expect(await screen.findByText(/network error/i)).toBeInTheDocument();

You're unit-testing "does my component handle the data/errors my boundary returns?" — not "does fetch construct a Response correctly?" That's why Lesson 10 put all as T and res.ok in one file, and tests mock that same file.

// satisfies — check shape, keep literals:
const theme = { primary: "#000", secondary: "#fff" } satisfies Theme;
type Primary = typeof theme.primary; // "#000"

// as const — readonly literals:
const ROLES = ["admin", "member"] as const;
type Role = typeof ROLES[number]; // "admin" | "member"

// branded IDs — nominal typing, zero runtime:
type UserId = string & { readonly __brand: "UserId" };
type PostId = string & { readonly __brand: "PostId" };
function toUserId(raw: string): UserId { return raw as UserId; }
