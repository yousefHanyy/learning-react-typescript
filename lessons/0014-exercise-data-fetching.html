Challenge 0 · Judgment drill

Generic, concrete, or union?

Objective: apply the one-job model until it's reflexive. No coding — verdict + deciding test out loud.

  1. function formatDate<T extends Date>(d: T): string
  2. function groupBy<K extends string, V>(items: V[], key: (v: V) => K): Record<K, V[]>
  3. A status prop that can only ever be "open" | "closed"
  4. function usePrevious<T>(value: T): T | undefined — returns the value from the last render
  5. function clamp<T extends number>(n: T, min: number, max: number): number
  6. function parseJSON<T>(raw: string): T

Solutions — with the deciding test for each

  1. Concrete. Single-use test: T appears once and links nothing. (d: Date) is identical power.
  2. Generic (correlation). The SAME V flows from items into the record's values, and K ties keyFn's return to the dictionary's keys. Break either link and callers lose type safety — duplication test passes hard: you'd need a copy per shape.
  3. Union. Closed set known today. A generic constraint would be ceremony over exactly two members.
  4. Generic (correlation). Input and output are THE SAME caller type across renders — Job 1 in its purest form. Concrete is impossible: every caller has a different type.
  5. Concrete. Single-use test: nothing correlates, and note the return isn't even T — it's plain number. The constraint did all the work, so delete it.
  6. Generic (caller knows best). The implementation cannot know what raw holds — Job 2. Same deal as getJSON: declaration lives at the call site, ideally near runtime validation.

Scoring honestly: 6/6 with reasons → the model stuck. Any miss on 1/5/6 → reread the single-use test in Lesson 4; those three are the same trap wearing different hats.

Challenge 1 · Lesson 9

Build an Avatar polymorphic component

Objective: the full pattern from scratch — constraint, own props, default tag.

An Avatar usually renders an <img>, but clickable avatars must render as <a> or a router link.
  • Own props: src?: string (only meaningful for images), size?: "sm" | "md" | "lg"
  • as swaps the element; default "img"
  • Must compile: <Avatar src="/me.png" /> and <Avatar as="a" href="/profile" />
  • Must NOT compile: <Avatar href="/profile" /> (no as)

Solution

import * as React from "react";

interface AvatarOwnProps<E extends React.ElementType> {
  src?: string;
  size?: "sm" | "md" | "lg";
  as?: E;
}

type AvatarProps<E extends React.ElementType> =
  React.ComponentPropsWithRef<E> & AvatarOwnProps<E>;

export function Avatar<E extends React.ElementType = "img">({
  size = "md",
  as,
  ...rest
}: AvatarProps<E>) {
  const Tag = as ?? "img";
  return <Tag {...rest} />;
}

The no-as rejection falls out for free: without it, E defaults to "img", whose props have no href. Note this is the corrected shape from the lesson — own props are generic (AvatarOwnProps<E>) because as?: E needs the parameter.

Challenge 2 · Lesson 10

Fix the broken fetch layer

Objective: spot the two classic bugs before running anything.

This wrapper ships Friday. Find both bugs and state their symptom: 
async function fetchPosts(): Promise<Post[]> {
  const res = await fetch("/api/posts");
  const posts = await res.json();
  return posts;
}

Solution

  1. No res.ok check. Symptom: a 500 response resolves happily, .json() parses the error body, and the app renders "valid" garbage — or crashes later on a missing field. Remember: fetch only rejects on network failure, never HTTP status.
  2. Silent assertion. res.json() is any, so returning it as Post[] compiles with zero acknowledgment of the trust boundary. Not wrong to assert — wrong to do it invisibly and scattered. Make it explicit and centralized:
async function fetchPosts(): Promise<Post[]> {
  const res = await fetch("/api/posts");
  if (!res.ok) throw new Error(`Posts failed: ${res.status}`);
  return (await res.json()) as Post[];
}

Bonus point if you also flagged: no way for callers to distinguish loading/error yet — that's Challenge 3's job.

Challenge 3 · Lesson 10

useSearchResults — the full machine

Objective: FetchState machine + hook + narrowed consumption, end to end.

Build search against /api/search?q=…:
  • useSearch(query) returns a FetchState<Result[]>-style union — design the members
  • Refetches when query changes; stale responses must not win (typing fast!)
  • Component renders: loading text / result list / error alert — data access must be impossible outside success

Solution

interface Result {
  id: string;
  title: string;
}

type SearchState =
  | { status: "idle" }                        // empty query — not an error!
  | { status: "loading" }
  | { status: "success"; data: Result[] }
  | { status: "error"; message: string };

function useSearch(query: string): SearchState {
  const [state, setState] = useState<SearchState>({ status: "idle" });

  useEffect(() => {
    if (!query.trim()) return;                // idle stays idle
    let cancelled = false;
    setState({ status: "loading" });

    getJSON<Result[]>(`/api/search?q=${encodeURIComponent(query)}`)
      .then((data) => { if (!cancelled) setState({ status: "success", data }); })
      .catch((err) => { if (!cancelled) setState({ status: "error", message: String(err) }); });

    return () => { cancelled = true; };
  }, [query]);

  return state;
}

function SearchPanel({ query }: { query: string }) {
  const state = useSearch(query);

  switch (state.status) {
    case "idle":     return null;
    case "loading":  return <p>Searching…</p>;
    case "success":
      return (
        <ul>
          {state.data.map((r) => <li key={r.id}>{r.title}</li>)}
        </ul>
      );
    case "error":
      return <p role="alert">{state.message}</p>;
  }
}

Details worth self-checking: the "idle" member exists so an empty query box isn't a lie ("loading" forever); cancelled flips during cleanup so a slow old request can't overwrite a fresh one's results; and state.data.map compiling at all proves the discriminant narrowing held.

Stretch · Lessons 9 + 10

Paginated table, both lessons combined

Objective: production-grade composition — polymorphic shell around fetching state.

A user directory: paginated API (/api/users?page=N), rows that link to profiles.
  • Type the page envelope: { items: User[]; total: number }
  • Fetch per page with the state machine; Next/Prev buttons disabled appropriately (loading or boundary pages)
  • Rows render through a polymorphic component so each row can be an <a> — but the table itself doesn't care what it wraps
Design freely; the grading criteria are the types, not pixel details.

Solution

interface UserPage {
  items: User[];
  total: number;
}

function Directory() {
  const [page, setPage] = useState(1);
  const state = useFetch<UserPage>(`/api/users?page=${page}`);

  if (state.status !== "success") {
    return <p>{state.status === "error" ? state.message : "Loading…"}</p>;
  }

  const { items, total } = state.data;
  const maxPage = Math.ceil(total / 25);

  return (
    <>
      <table>
        <tbody>
          {items.map((u) => (
            <tr key={u.id}>
              <td>
                <Avatar as="a" href={`/users/${u.id}`} src={u.avatar} size="sm">
                  {u.name}
                </Avatar>
              </td>
              <td>{u.email}</td>
            </tr>
          ))}
        </tbody>
      </table>
      <button disabled={page <= 1 || state.status === "loading"} onClick={() => setPage(page - 1)}>
        Prev
      </button>
      <button disabled={page >= maxPage || state.status === "loading"} onClick={() => setPage(page + 1)}>
        Next
      </button>
    </>
  );
}

What's being graded under the hood:

  1. Envelope typing mirrors the server contract exactly — items + total, no invented optionals.
  2. Early return narrows everything below it to success — cleaner than switch when one branch dominates. After the guard, state.data is free of checks.
  3. Avatar-as-link shows why the polymorphic pattern exists: the table composes rows without knowing they're anchors; E infers "a", so href type-checks while disabled wouldn't.

Note one deliberate wrinkle: state.status === "loading" inside the success block would always be false — after the early return TS has already narrowed it away. If you wrote that check anyway, TS flags it as impossible. That contradiction is the machine working.
