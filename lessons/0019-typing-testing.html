Setup — two files, then forget it

Real codebases use Vitest + jsdom (a fake browser in Node). Two config files, then every test looks like Jasmine:

// vitest.config.ts — copy once, never touch again
import react from "@vitejs/plugin-react";
import { defineConfig } from "vitest/config";
export default defineConfig({
  plugins: [react()],
  test: { environment: "jsdom", setupFiles: "./vitest.setup.ts" },
});
// vitest.setup.ts
import "@testing-library/jest-dom/vitest"; // adds .toBeInTheDocument()

Install: vitest jsdom @testing-library/react @testing-library/jest-dom @testing-library/user-event @vitejs/plugin-react

Your first test, line by line

Same pattern as Jasmine — render, find, interact, assert. Only the query is new:

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

// Component under test — just a button with a callback prop:
function Counter({ onSave }: { onSave: (n: number) => void }) {
  return <button onClick={() => onSave(42)}>Save</button>;
}

// This block is Jasmine you already know:
test("calls onSave with 42", async () => {
  // 1. Arrange — create a spy (Jasmine: jasmine.createSpy(), here: vi.fn())
  const onSave = vi.fn(); // fake function that records every call

  // 2. Render — puts <Counter> into jsdom's fake DOM (new vs Jasmine):
  render(<Counter onSave={onSave} />);

  // 3. Find — ask "what would a screen reader find?" (new vs Jasmine):
  //    getByRole throws if not found — use it when the element MUST exist.
  const btn = screen.getByRole("button", { name: /save/i });

  // 4. Interact — like a real user (new vs Jasmine's fireEvent):
  const user = userEvent.setup(); // create a user once per test
  await user.click(btn);          // fires pointerDown → focus → click, not just click

  // 5. Assert — Jasmine you already know:
  expect(onSave).toHaveBeenCalledWith(42);
});

Queries — which to reach for

Priority engineers will expect you to follow (most accessible first):

  1. getByRole with name — buttons, headings, links — mirrors screen readers
  2. getByLabelText — inputs with <label>
  3. getByText — plain text / paragraphs
  4. getByTestId — last resort only (adds data-testid to production DOM)
Three variants, three jobs:
  • getBy* — throws if not found. Use when the element MUST exist.
  • queryBy* — returns null if not found. Use to assert absence: expect(screen.queryByText("Error")).not.toBeInTheDocument()
  • findBy* — async, waits for the element to appear (we'll use it for fetching in 13b).

What vi.fn() / createSpy actually does

Both do the same thing — create a fake function that remembers every call so you can ask what happened:

// Jasmine you know:
const spy = jasmine.createSpy("onSave");
spy(42);
spy(99);
expect(spy).toHaveBeenCalled();              // was it called at all?
expect(spy).toHaveBeenCalledWith(42);        // was it called with 42?
expect(spy).toHaveBeenCalledTimes(2);        // how many times?
spy.calls.reset(); // clear history between tests

// Vitest — identical, just renamed:
const onSave = vi.fn(); // ← fake function, empty history
onSave(42);
onSave(99);
expect(onSave).toHaveBeenCalledWith(42);
expect(onSave).toHaveBeenCalledTimes(2);
onSave.mockClear(); // same as .calls.reset()

You pass the spy as a prop (<Counter onSave={onSave} />) to prove the component called it correctly — without needing the real implementation. In TS you can add a type hint when you want: vi.fn<(n: number) => void>() — but plain vi.fn() works fine to start, just like Jasmine.

Recipe: your first test (Jasmine → Vitest)

  1. Create a spy: const onSave = vi.fn() (was jasmine.createSpy()).
  2. Render: render(<Component onSave={onSave} />).
  3. Find: screen.getByRole("button", { name: /save/i }) first, getByTestId last.
  4. Interact: const user = userEvent.setup(); await user.click(btn) (not fireEvent).
  5. Assert: expect(onSave).toHaveBeenCalledWith(42) — Jasmine you know.
