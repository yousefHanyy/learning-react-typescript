The schema is the type

Lesson 8 left you writing validation by hand — if (typeof name !== "string") per field. Real codebases don't. They declare one schema and derive everything from it. If the schema says email is required, the TypeScript type says so too — no drift, no duplicate interface.

import { z } from "zod";

const signUpSchema = z.object({
  name: z.string().min(2, "Name is too short"),
  email: z.string().email("Invalid email"),
  age: z.number().min(18, "Must be 18+"),
  role: z.enum(["admin", "member"]),   // ← union, not bare string
});

// ONE definition, the type comes for free:
type SignUpValues = z.infer<typeof signUpSchema>;
//   ^ { name: string; email: string; age: number; role: "admin" | "member" }

Rule: never hand-write an interface that mirrors a zod schema. z.infer is the interface. When the schema changes, every consumer updates — no manual sync.

Need the input shape (before transforms/coercions) separately? z.input<typeof schema> vs z.output. For most forms without transforms, they're identical and z.infer (which is z.output) is all you need.

Wiring React Hook Form + zodResolver

react-hook-form handles state, submission, and re-render optimization. zodResolver is the glue that makes it validate against your schema before handleSubmit ever fires.

import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";

const schema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
});

type Values = z.infer<typeof schema>;

function SignUpForm() {
  const {
    register,           // wires an <input> to the form
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm<Values>({
    resolver: zodResolver(schema),
    defaultValues: { name: "", email: "" },   // must satisfy Values
  });

  const onSubmit = (data: Values) => {
    // data is VALIDATED — zod already ran; email is a real email here
    console.log(data);
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register("name")} />
      {errors.name && <p>{errors.name.message}</p>}
      <input {...register("email")} />
      {errors.email && <p>{errors.email.message}</p>}
      <button disabled={isSubmitting}>Submit</button>
    </form>
  );
}

What the generics buy you:

  • register("name") — autocomplete for field names, compile error on register("nmae"). The string is typed as Path<Values> (all valid dot-paths into Values).
  • handleSubmit(onSubmit) — onSubmit receives Values, not FormData. No formData.get narrowing needed.
  • errors is FieldErrors<Values> — each key is optional and carries .message from the schema.
Setup note: install react-hook-form, zod, and @hookform/resolvers. That's it — no extra config. Every codebase using this stack follows the exact wiring above.

Defaults, numbers, and error shapes

Three things juniors get wrong in week one:

  1. defaultValues must match the schema. Omit a required field or use the wrong type → compile error immediately. Let the error guide you.
  2. Number inputs are strings in the DOM. Use schema coercion or RHF's value transform — otherwise "42" fails z.number():
// Option A — zod coerces the string for you:
const schema = z.object({ age: z.coerce.number().min(18) });

// Option B — RHF parses it before validation:
<input type="number" {...register("age", { valueAsNumber: true })} />

Pick one per field, not both. Coercion in zod is more common because the transform stays with the schema.

// errors is deeply typed — safe to render per-field:
{errors.email?.message && <p role="alert">{errors.email.message}</p>}
//       ^ string | undefined — exactly what <p> wants

When register isn't enough: Controller

register works for native <input>/<select>. For controlled components (a custom <DatePicker>, MUI <Select>, any component that takes value/onChange as props), use Controller:

import { Controller } from "react-hook-form";

<Controller
  name="role"                 // still typed as Path<Values>
  control={control}
  render={({ field }) => (
    <Select
      value={field.value}
      onValueChange={field.onChange}
      onBlur={field.onBlur}
    />
  )}
/>

field is typed to the field's value ("admin" | "member" here) — onValueChange can't be called with a stray string. The same Path safety as register, just for controlled UI. How it gets that type:

// Controller is generic in two slots — you never write them, inference does:
type ControllerProps<
  TFieldValues extends FieldValues,          // ← from control={control}  (Control<Values>)
  TName extends FieldPath<TFieldValues>     // ← from name="role"        (Path<Values>)
>

<Controller
  name="role"            // TName = "role"
  control={control}      // TFieldValues = Values  →  ties the two together
  render={({ field, fieldState, formState }) => {
    // field:      ControllerRenderProps<Values, "role">
    // field.value: FieldPathValue<Values, "role">  →  "admin" | "member"
    // field.onChange: (...event: any[]) => void   →  wired to RHF's state
    // fieldState: { invalid, isDirty, error?: FieldError }
    // formState:  whole form's state (isSubmitting, etc.)
    return <Select value={field.value} onValueChange={field.onChange} />;
  }}
/>

Yes — render is the render-prop pattern from Lesson 4 and reference §5. It's the textbook case where hooks alone don't suffice: Controller must own the field lifecycle (registration, validation, value subscription) the way a hook owns logic — but it can't know what JSX you want to wrap (a MUI Select? a custom DatePicker?). The only way to give you the typed field object while letting you choose the UI is to call a function you provide with that object — that's the render prop. Modern rule still holds: prefer hooks by default; this is the narrow survivor where the wrapper genuinely owns rendering around your content. The hook equivalent useController({ name, control }) returns the same { field, fieldState } — use it when you prefer hooks over JSX, but Controller's render is more ergonomic for inline UI.

Rule of thumb: native element → register. Anything with value/onChange props → Controller (or useController if you want the hook form).

Input vs output — the transform trap

Most forms submit exactly what the user typed. When a field transforms (e.g. a comma-separated string → string array), the stored type and the submitted type diverge. RHF's useForm has a third generic for that:

const schema = z.object({
  tags: z.string().transform(s => s.split(",").map(t => t.trim())),
  // input:  { tags: string }
  // output: { tags: string[] }
});

type Input = z.input<typeof schema>;   // what register/watch see
type Output = z.output<typeof schema>; // what handleSubmit receives

const { register, handleSubmit } = useForm<Input, unknown, Output>({
  resolver: zodResolver(schema),
});

const onSubmit = (data: Output) => {
  data.tags.map(...)  // tags is string[] here — correctly
};

Without the third generic, data.tags would still be typed as string and .map would be wrong. As a junior you'll hit this rarely — but when a transform exists, this is the one line that makes it type-safe. For the 90% of forms with no transforms, ignore it entirely.

Recipe: typed forms with Zod + RHF

  1. Define a zod schema per form — z.object({ ... }). This is the only place field rules live.
  2. Derive the type: type Values = z.infer<typeof schema> — never duplicate as an interface.
  3. Wire the form: useForm<Values>({ resolver: zodResolver(schema), defaultValues }).
  4. Native inputs → {...register("fieldName")}. Controlled components → <Controller name="..." control={control} render={({ field }) => ...} />.
  5. Number inputs: z.coerce.number() in the schema (prefer) or register("age", { valueAsNumber: true }).
  6. Submit: handleSubmit((data: Values) => ...) — data is already validated, no FormData.get narrowing.
  7. Errors: formState.errors is FieldErrors<Values> — render errors.field?.message per field.
  8. Transforms? Add the third generic: useForm<Input, unknown, Output> so handleSubmit sees the output type.
