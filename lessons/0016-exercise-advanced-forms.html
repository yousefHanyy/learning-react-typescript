How to do this: one schema = one type — if you catch yourself writing an interface that mirrors a schema, stop. Reveal only after you have a compiling answer.
Challenge 1 · The schema IS the type

Fix the drift

Objective: eliminate a duplicated interface and let z.infer be the single source of truth.

This code shipped — then the schema added role and the interface didn't: 
interface SignUpFormValues {
  name: string;
  email: string;
}

const signUpSchema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
  role: z.enum(["admin", "member"]),
});

// later:
type Values = SignUpFormValues; // ← bug: missing role, still compiles
Fix it: derive the type from the schema, delete the interface, and show what z.infer gives you. What breaks if you keep both?

Solution

const signUpSchema = z.object({
  name: z.string().min(2),
  email: z.string().email(),
  role: z.enum(["admin", "member"]),
});

type SignUpValues = z.infer<typeof signUpSchema>;
//   ^ { name: string; email: string; role: "admin" | "member" }

// delete the interface entirely — it was the drift source

Keeping both means every schema change needs a manual interface edit — missed once, the types lie and role is silently undefined at runtime while TS thinks it can't be. One source of truth fixes it forever.

Challenge 2 · Wiring

Wire a login form end-to-end

Objective: useForm + zodResolver with typed register and FieldErrors.

Build a login form:
  • Schema: email (valid email) and password (min 8) — both required
  • defaultValues must satisfy the type — make it compile
  • Wire register for both fields; render errors.email?.message per field
  • handleSubmit receives validated data — no FormData.get
  • Bonus: what happens if you typo register("emial")?

Solution

import { useForm } from "react-hook-form";
import { zodResolver } from "@hookform/resolvers/zod";
import { z } from "zod";

const loginSchema = z.object({
  email: z.string().email("Invalid email"),
  password: z.string().min(8, "At least 8 characters"),
});

type LoginValues = z.infer<typeof loginSchema>;

function LoginForm() {
  const {
    register,
    handleSubmit,
    formState: { errors, isSubmitting },
  } = useForm<LoginValues>({
    resolver: zodResolver(loginSchema),
    defaultValues: { email: "", password: "" },
  });

  const onSubmit = (data: LoginValues) => {
    // data.email is a valid email here — zod already ran
    console.log(data);
  };

  return (
    <form onSubmit={handleSubmit(onSubmit)}>
      <input {...register("email")} placeholder="email" />
      {errors.email && <p role="alert">{errors.email.message}</p>}
      <input type="password" {...register("password")} />
      {errors.password && <p role="alert">{errors.password.message}</p>}
      <button disabled={isSubmitting}>Log in</button>
    </form>
  );
}

Bonus: register("emial") is a compile error — the argument is Path<LoginValues>, so only "email" | "password" are allowed. That's the payoff vs stringly-typed formData.get.

Challenge 3 · Controller

Wrap a controlled Select

Objective: decide register vs Controller and type the render prop.

Your design system has <RoleSelect value={...} onValueChange={...} /> (controlled, not a native <select>).
  • Add role: z.enum(["admin","member","viewer"]) to the schema from Challenge 2
  • Wire it with Controller — register won't work here, say why
  • In render, destructure { field, fieldState } and annotate what field.value and fieldState.error are

Solution

const schema = z.object({
  email: z.string().email(),
  password: z.string().min(8),
  role: z.enum(["admin", "member", "viewer"]),
});
type Values = z.infer<typeof schema>;

import { Controller } from "react-hook-form";

function Form() {
  const { control, handleSubmit } = useForm<Values>({
    resolver: zodResolver(schema),
    defaultValues: { email: "", password: "", role: "viewer" },
  });

  return (
    <form onSubmit={handleSubmit((data) => console.log(data))}>
      {/* ...email/password via register... */}
      <Controller
        name="role"              // Path<Values> — typo here also fails
        control={control}        // Control<Values> — ties TFieldValues
        render={({ field, fieldState }) => {
          // field: ControllerRenderProps<Values, "role">
          // field.value: "admin" | "member" | "viewer"
          // fieldState.error?: FieldError
          return (
            <RoleSelect
              value={field.value}
              onValueChange={field.onChange}
              onBlur={field.onBlur}
            />
          );
        }}
      />
    </form>
  );
}

register spreads props onto a native input — it can't drive a component that owns value/onChange. That's exactly the render-prop survivor case from Lesson 4: the wrapper must own the field lifecycle but can't know your JSX.

Challenge 4 · Numbers

The age field that never validates

Objective: fix the string-in-DOM vs z.number() mismatch.

This always fails validation — why? Fix it one way and justify your pick: 
const schema = z.object({ age: z.number().min(18) });
<input type="number" {...register("age")} />

Solution

DOM inputs always emit string — so "22" (string) hits z.number() and fails.

// Fix A — zod coerces (preferred: transform stays with schema):
const schema = z.object({ age: z.coerce.number().min(18) });
<input type="number" {...register("age")} />

// Fix B — RHF parses before validation:
<input type="number" {...register("age", { valueAsNumber: true })} />

Pick one, not both. Coercion in zod is the common choice because future consumers of the schema get the same behavior without remembering the register option.

Stretch · Input vs Output

Comma-separated tags → string array

Objective: the third generic — when handleSubmit's type must diverge from the inputs.

A "tags" field takes "react, typescript, zod" as text but should submit as string[].
  • Schema: tags: z.string().transform(s => s.split(",").map(t => t.trim()).filter(Boolean))
  • Wire useForm so onSubmit receives { tags: string[] } — not { tags: string }
  • What types do register("tags") and data.tags have respectively?

Solution

const schema = z.object({
  tags: z.string().transform(s => s.split(",").map(t => t.trim()).filter(Boolean)),
});

type Input = z.input<typeof schema>;   // { tags: string }
type Output = z.output<typeof schema>; // { tags: string[] }

const { register, handleSubmit } = useForm<Input, unknown, Output>({
  resolver: zodResolver(schema),
  defaultValues: { tags: "" },
});

const onSubmit = (data: Output) => {
  data.tags.map(t => t.toUpperCase()); // string[] — correct after transform
};

// register("tags") works on Input  — the raw string in the input
// data.tags in onSubmit is string[] — the transformed output

Without the third generic (Output), data.tags stays typed as string and .map would be an error. This is the one line juniors add only when a transform exists — 90% of forms skip it entirely.

All done? You now own the form pattern real codebases expect on day one: schema → inferred type → resolver → register/Controller. No FormData.get narrowing, no interface drift.
