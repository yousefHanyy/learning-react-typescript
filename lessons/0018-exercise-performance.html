Challenge 1 · Spot the useless memo

Why does this memoized list still jank?

Objective: apply the shallow-compare rule.

const Row = memo(function Row({ user, onSelect }: RowProps) {
  return <li onClick={() => onSelect(user.id)}>{user.name}</li>;
});

function List({ users }: { users: User[] }) {
  return (
    <ul>
      {users.map(u => (
        <Row key={u.id} user={u} onSelect={(id) => console.log(id)} />
      ))}
    </ul>
  );
}
The profiler shows List re-rendering 60fps and every Row along with it despite memo. Name the two stable-props violations and what memo actually does here (hint: cost without benefit).

Solution

  • onSelect={(id) => console.log(id)} — new arrow every List render → new function reference → prevProps.onSelect !== nextProps.onSelect → bail-out fails for every Row.
  • If users itself is a new array each render (e.g. users={data.map(...)} inline in parent), then user={u} is also a new object per row even when data is equal.

Result: memo shallow-compares props, fails, and still renders — you pay the comparison cost and the render. Juniors add memo for speed and get slower.

Challenge 2 · Fix it

Make memo actually bail out

Objective: stabilize object + function props.

Fix Challenge 1 so Row can skip when users haven't changed. Requirements:
  • onSelect must be stable across renders
  • users filtering (if any) must be stable — show where useMemo belongs
  • Keep types inferred — no extra generics

Solution

function List({ users }: { users: User[] }) {
  const handleSelect = useCallback((id: string) => {
    console.log(id);
  }, []); // stable — no deps that change per render

  // if filtering/sorting, memo the derived array itself:
  const visibleUsers = useMemo(
    () => users.filter(u => u.active),
    [users]
  );

  return (
    <ul>
      {visibleUsers.map(u => (
        <Row key={u.id} user={u} onSelect={handleSelect} />
      ))}
    </ul>
  );
}

Now prevProps.onSelect === nextProps.onSelect and prevProps.user === nextProps.user (same object from stable array) — shallow compare succeeds and inactive rows skip.

Common mistake: memoizing the list but still passing onSelect={() => ...} inline — one unstable prop defeats the whole optimization.

Challenge 3 · Typing

Type the hooks without over-annotating

Objective: inferred vs explicit handler typing.

For each, say what TypeScript infers and when you'd add an explicit type:
  1. const visible = useMemo(() => users.filter(u => u.active), [users])
  2. const handleChange = useCallback((e) => setValue(e.currentTarget.value), []) — passed as onChange to a typed <input>
  3. const next = useMemo(() => found ? found.name : null, [found])

Solution

  1. visible: User[] — inferred from filter's return. No generic needed.
  2. (e: any) => void inferred as untyped param — e.currentTarget is any. Fix with explicit handler type: 
    const handleChange = useCallback<React.ChangeEventHandler<HTMLInputElement>>(
  e => setValue(e.currentTarget.value),
  []
);
    Now e.currentTarget.value is string and mismatched handlers don't compile.
  3. string | null — inferred, but if found is User | undefined, inference may widen to string | null | undefined. Pin it when needed: 
    const next = useMemo<string | null>(() => found ? found.name : null, [found]);
    Rule: infer by default, annotate only when the factory's branches make the type ambiguous.
Challenge 4 · Judgment

Memo or not?

Objective: the checklist from the lesson.

For each, say memo / don't memo and which checklist item decides it:
  1. A single <Header> with two strings as props, rendering once per page
  2. A 500-row virtualized table where rows are pure and props are stable
  3. A form <Input> that receives style={{ marginBottom: 8 }} inline
  4. A chart that runs a 50ms filter on 10k points — profiler shows jank on every keystroke

Solution

  1. Don't memo — not expensive/many (checklist item 3). Cost > benefit.
  2. Memo — measured? yes (many), stable? yes (by design), expensive/many? yes (500). All three pass.
  3. Don't memo (or fix props) — fails checklist item 2: inline {{ marginBottom: 8 }} is a new object each render, so memo never bails out. Fix with useMemo or extract constant, then memo helps.
  4. Memo the value, not necessarily the component — useMemo(() => heavyFilter(data), [data]) caches the 50ms work. Memoizing the chart component alone still recomputes the filter if the prop array is new.
Stretch · The inline trap, quantified

Prove it to yourself

Objective: see the reference vs deep-equality gap in devtools.

Add a console.log("Row render", user.id) inside a memo(Row), then toggle between:
  • <Row config={{ theme: "light" }} /> (inline)
  • const config = useMemo(() => ({ theme: "light" as const }), []); <Row config={config} />
Trigger a parent re-render (e.g. unrelated counter). Count renders in each case. Why does case 1 log every time while case 2 stays silent?

Solution

Case 1 allocates a new { theme: "light" } each parent render → prevConfig !== nextConfig → memo bails out never → log every time. Case 2 returns the same reference → prevConfig === nextConfig → memo skips → silent. This is referential identity, not deep equality — the single most common performance bug juniors ship.

Done? The takeaway is negative: the skill is knowing when not to memo. Default to no memo, measure, then stabilize only the props that break the bail-out.
