Lesson 2

Typing Events & State

~6 min · Builds on: Lesson 1 · Glossary

← Lesson 1: Typing Props Next: Refs & forwardRef

Two things you'll type every single day at work: event handlers and state. Both are simpler than they first look.

1. Event handlers

React exports a handler type for every event. Use React.XEventHandler<HTMLElement> when you pass a handler as a named function:

// onChange on an input → ChangeEvent
function App() {
  const handleChange = (e: React.ChangeEvent<HTMLInputElement>) => {
    console.log(e.currentTarget.value);
  };

  return <input onChange={handleChange} />;
}

When the handler is inline in JSX, you can skip the type entirely — TS infers it from the element:

function App() {
  return (
    <input onChange={(e) => console.log(e.currentTarget.value)} />
    //       ↑ e is inferred as ChangeEvent<HTMLInputElement>
  );
}
Key types: React.ChangeEvent<HTMLInputElement> (onChange), SubmitEvent (onSubmit), React.MouseEvent<HTMLButtonElement> (onClick). The generic is always the element the event is attached to. Note: React.FormEvent was deprecated in @types/react 19.2.10 — use SubmitEvent / SubmitEventHandler for forms.

2. useState inference

TS infers state type from the initial value. This causes a bug — the classic empty-array trap:

const [items, setItems] = useState([]);
// items: never[]  ← you can't add anything!

setItems([...items, { id: 1, name: 'A' }]); // ❌ error

Fix: annotate useState with the element type:

interface Item { id: number; name: string; }

const [items, setItems] = useState<Item[]>([]);
setItems([...items, { id: 1, name: 'A' }]); // ✅

3. Union state (the workhorse)

This is the pattern you'll see in real apps for anything async — fetch results, auth, modals. It's the type union from Lesson 1 applied to state:

type RequestState =
  | { status: 'idle' }
  | { status: 'loading' }
  | { status: 'success'; data: Item[] }
  | { status: 'error'; error: string };

const [request, setRequest] = useState<RequestState>({ status: 'idle' });

function load() {
  setRequest({ status: 'loading' });
  fetchData().then(
    (data) => setRequest({ status: 'success', data }),
    (error) => setRequest({ status: 'error', error: error.message }),
  );
}

Because status is a discriminator, TS narrows the shape for you:

if (request.status === 'success') {
  // ✅ request.data is Item[] here, guaranteed
  request.data.map((item) => <p>{item.name}</p>);
} else if (request.status === 'error') {
  // ✅ request.error is string here
}
Why this beats a boolean isLoading flag: it encodes all possible states at once, and the compiler catches illegal combinations (e.g., data present while loading). No more "does data exist?" checks.

Recipe: events & state

Events:

  1. Inline handler in JSX → no annotation needed (TS infers)
  2. Named/extracted handler → annotate the param: (e: React.ChangeEvent<HTMLInputElement>)
  3. Form submit → SubmitEvent; the generic is always the element the event fires on

State:

  1. Initial value exists → let inference work: useState(0), useState('a')
  2. Empty array or null start → annotate explicitly: useState<Item[]>([])
  3. Async / multi-phase data → discriminated union with a status field
Primary source: React's official TypeScript guide on state & hooks.
