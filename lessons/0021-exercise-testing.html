Challenge 1 · Your first spy

Counter calls onSave

Objective: vi.fn() is jasmine.createSpy() — create, pass, assert.

function Counter({ onSave }: { onSave: (n: number) => void }) {
  return <button onClick={() => onSave(42)}>Save</button>;
}
Write a test that:
  • Creates a spy with vi.fn() (like jasmine.createSpy())
  • Renders <Counter onSave={spy} />
  • Finds the button by role and clicks it with userEvent
  • Asserts toHaveBeenCalledWith(42) and toHaveBeenCalledTimes(1)
No types needed yet — plain vi.fn() is fine.

Solution

import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";

test("calls onSave with 42", async () => {
  const onSave = vi.fn(); // ← standalone fake — you created it
  render(<Counter onSave={onSave} />);

  const btn = screen.getByRole("button", { name: /save/i }); // most accessible query
  await userEvent.setup().click(btn); // real user sequence, not just click event

  expect(onSave).toHaveBeenCalledWith(42);
  expect(onSave).toHaveBeenCalledTimes(1);
});

Add the type later when you want the compiler to guard it: vi.fn<(n: number) => void>() then onSave("oops") becomes a compile error — same spy, just tighter.

Challenge 2 · Queries

Fix the query priority

Objective: getByRole first, getByTestId last.

This test works but would fail code review — why? Refactor it to use the priority from Lesson 13a: 
render(<LoginForm />);
const input = screen.getByTestId("email-input"); // ❌
const btn = screen.getByTestId("submit-btn");    // ❌
await userEvent.setup().click(btn);
expect(screen.getByText("Sign in")).toBeInTheDocument(); // ❌ for a button
Rewrite with the correct queries and explain which variant (getBy / queryBy / findBy) you'd use to assert "error is NOT on screen."

Solution

render(<LoginForm />);

// 1. inputs with labels → getByLabelText:
const input = screen.getByLabelText(/email/i);
// 2. buttons → getByRole with name:
const btn = screen.getByRole("button", { name: /sign in/i });
await userEvent.setup().click(btn);
// 3. after submit, assert absence with queryBy (returns null if missing):
expect(screen.queryByText(/invalid email/i)).not.toBeInTheDocument();

getByTestId adds prod-only attributes and skips accessibility — last resort. getBy* throws if missing (for elements that must exist), queryBy* returns null (for absence), findBy* waits async (next challenge).

Challenge 3 · Real provider

Wrap, don't mock the hook

Objective: real <AuthProvider> wrapper vs faking useAuth.

function Profile() {
  const { user } = useAuth(); // throws if outside a provider
  return <p>Welcome, {user.name}</p>;
}
Write two versions and label which is "real":
  1. Using vi.mock("../auth", () => ({ useAuth: () => fake }))
  2. Using render(<Profile />, { wrapper: AuthProvider })
Say why 2) is the default and when you'd still need to fake (hint: seeding a specific state like "admin").

Solution

// ❌ Not real — bypasses AuthProvider's useState/memo logic, drifts when
//    AuthContextValue adds signOut:
vi.mock("../auth", () => ({ useAuth: () => ({ user: fakeUser }) }));
render(<Profile />);

// ✅ Real — runs the actual provider, catches provider bugs:
import { AuthProvider } from "../auth";
render(<Profile />, {
  wrapper: ({ children }) => <AuthProvider>{children}</AuthProvider>,
});
expect(screen.getByText(/welcome, ada/i)).toBeInTheDocument();

// hooks too:
const { result } = renderHook(() => useAuth(), {
  wrapper: ({ children }) => <AuthProvider>{children}</AuthProvider>,
});

Need "logged-in as admin" without doing a login? Seed the real provider: <AuthProvider initialUser={admin}> — still the real component, just with test data. Mock the hook only as an escape hatch.

Challenge 4 · Mock the boundary

UserList that fetches

Objective: mock api.getJSON (the boundary), not fetch.

// api.ts — the ONE place as T lives (Lesson 10):
export async function getJSON<T>(url: string): Promise<T> { ... }
// UserList.tsx calls getJSON internally:
function UserList() {
  const state = useFetch<User[]>("/api/users");
  if (state.status !== "success") return <p>Loading…</p>;
  return <ul>{state.data.map(u => <li key={u.id}>{u.name}</li>)}</ul>;
}
Write a test that:
  • Spies on api.getJSON (not global.fetch) with mockResolvedValue
  • Renders <UserList /> and waits with findByText
  • Asserts toHaveBeenCalledWith("/api/users") (auto-typed)
  • Then a second test where the boundary rejects and the error UI appears — use mockRejectedValue
Say why mocking fetch is the wrong answer.

Solution

import * as api from "../api";

test("shows users", async () => {
  const spy = vi.spyOn(api, "getJSON").mockResolvedValue([{ id: "1", name: "Ada" }]);

  render(<UserList />);
  expect(await screen.findByText("Ada")).toBeInTheDocument(); // findBy* waits async
  expect(spy).toHaveBeenCalledWith("/api/users"); // typed: (url: string)
  spy.mockRestore();
});

test("shows error when boundary fails", async () => {
  vi.spyOn(api, "getJSON").mockRejectedValue(new Error("Network error"));
  render(<UserList />);
  expect(await screen.findByText(/network error/i)).toBeInTheDocument();
  vi.restoreAllMocks();
});

Why not fetch? fetch is global — you fake Response objects by hand (untyped, leaks to other tests). Your boundary api.getJSON is local, typed, and the same file Lesson 10 centralized — mocking it tests "does my component handle what my wrapper returns?" not "does fetch construct a Response?"

Stretch · Async form

Zod blocks submit

Objective: findBy + waitFor + userEvent (Lesson 13b).

A LoginForm uses zodResolver — invalid email blocks onSuccess and renders the error. Write a test that:
  1. Clicks submit with empty fields → waits for "Invalid email" with findByText and asserts onSuccess = vi.fn() was NOT called
  2. Types a valid email/password with user.type, clicks again, then waits for the error to disappear (use waitFor + queryByText)

Solution

test("zod blocks, then submits", async () => {
  const user = userEvent.setup();
  const onSuccess = vi.fn();
  render(<LoginForm onSuccess={onSuccess} />);

  await user.click(screen.getByRole("button", { name: /sign in/i }));
  expect(await screen.findByText(/invalid email/i)).toBeInTheDocument();
  expect(onSuccess).not.toHaveBeenCalled(); // resolver is the gate

  await user.type(screen.getByLabelText(/email/i), "ada@example.com");
  await user.type(screen.getByLabelText(/password/i), "hunter42!!");
  await user.click(screen.getByRole("button", { name: /sign in/i }));

  await waitFor(() =>
    expect(screen.queryByText(/invalid email/i)).not.toBeInTheDocument()
  );
  expect(onSuccess).toHaveBeenCalled();
});

getBy* would throw immediately before React flushed — findBy* waits with a timeout for async UI after validation/fetch. That's the async pattern juniors miss.

All done? You now own the testing pattern real codebases expect: spy when you provide a callback, spyOn when you intercept a boundary, real provider wrappers, and findBy for async UI.
