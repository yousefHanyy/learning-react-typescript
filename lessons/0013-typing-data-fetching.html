The any at the boundary

Everything so far kept the compiler inside your codebase. Fetching breaks that: data arrives from a server as text, and TypeScript has no idea what's in it:

const res = await fetch("/api/users");
const users = await res.json();
//    ^ Promise<any> — json()'s actual return type.
//      users: any. Every property access compiles. Zero protection.

res.json() cannot know your schema — it parses whatever bytes arrived. So it returns any, and from there the compiler rubber-stamps everything: users.nmae (typo), users[0].address.city (doesn't exist) — all "fine" until runtime.

This boundary is where real projects make a choice:

  1. Assert and trust — declare what the server should send and cast once at the edge. Today's lesson. It's what most codebases do daily.
  2. Validate at runtime — parse with a schema library like zod: UserSchema.parse(json) checks every field and gives you the type from the same schema. What serious teams add once the API misbehaves. Know it exists; learn it when you hit a project using it.

Step 1: type the shapes

Before any fetching code, describe the data exactly as the API sends it — including things your UI doesn't show yet:

interface User {
  id: number;
  name: string;
  email: string;
  role: "admin" | "member";     // narrow unions beat string — free validation hints
}
Gotcha: don't weaken fields "to be safe" (id?: number). If the API guarantees it, say so. Optional-everything types push null-checks onto every consumer and hide real contract violations. If the API is genuinely inconsistent, that's what runtime validation (option 2) is for.

Step 2: a typed fetch wrapper

async function getJSON<T>(url: string): Promise<T> {
  const res = await fetch(url);

  if (!res.ok) {
    throw new Error(`Request failed: ${res.status} ${res.statusText}`);
  }

  return (await res.json()) as T;
}

// call site — T inferred from usage context or annotated:
const users = await getJSON<User[]>("/api/users");   // users: User[]

Two details carry the whole lesson:

  1. if (!res.ok) — the trap everyone hits: fetch does NOT reject on 404 or 500. It resolves happily; only network-level failures throw. Without this check, a failed request flows onward as "valid data" (usually {} or an error page HTML parsed as JSON). The wrapper turns HTTP failures into real exceptions, caught by your state machine.
  2. as T — the one sanctioned lie. You're telling the compiler "I've verified the server sends T here." It believes you and stops checking — which is precisely the deal: checking happens once, at this single choke point, instead of never or everywhere.
Rule: all as-assertions about external data live in ONE layer (this wrapper). If a type lie turns out wrong, you fix it in one file — not scattered across every component.

Step 3: the state machine hook

The Lesson 2 union-state pattern, made generic and reusable:

import { useEffect, useState } from "react";

type FetchState<T> =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: T }        // data lives HERE and only here
  | { status: "error"; message: string };

function useFetch<T>(url: string): FetchState<T> {
  const [state, setState] = useState<FetchState<T>>({ status: "idle" });

  useEffect(() => {
    let cancelled = false;                // guard against out-of-order responses
    setState({ status: "loading" });

    getJSON<T>(url)
      .then((data) => {
        if (!cancelled) setState({ status: "success", data });
      })
      .catch((err) => {
        if (!cancelled) setState({ status: "error", message: String(err) });
      });

    return () => { cancelled = true; };   // effect cleanup
  }, [url]);

  return state;
}

Note what the type does for the implementation: inside .then, T is already fixed by the caller — setState({ status: "success", data }) won't compile unless data really is T.

Step 4: consuming — narrowing makes bugs unrepresentable

function UserList() {
  const state = useFetch<User[]>("/api/users");

  switch (state.status) {
    case "idle":
    case "loading":
      return <p>Loading…</p>;
    case "success":
      return (
        <ul>
          {state.data.map((u) => <li key={u.id}>{u.name}</li>)}
          {/* ^ state.data: User[] — guaranteed. No ?., no !, no if */}
        </ul>
      );
    case "error":
      return <p role="alert">{state.message}</p>;
  }
}

state.data.map(...) cannot crash with "cannot read properties of undefined" — in the "success" branch the union has narrowed to the one member that HAS data. Compare with the classic isLoading / data? / error? triple-boolean approach, where every combination ("loading AND error AND data") is representable and each consumer re-defines precedence.

Design principle worth stealing: model states so illegal combinations are unrepresentable — then whole bug classes stop compiling instead of being debugged.

Recipe: typed data fetching

  1. Interface per API resource, field-for-field as the server sends (no defensive optionals).
  2. One getJSON<T>-style wrapper: check res.ok, throw on failure, single as T at the edge.
  3. Generic FetchState<T> union — idle / loading / success+data / error+message.
  4. Hook wraps the call; guard stale responses with a cancelled flag in cleanup.
  5. Components consume via switch (status) — data access only compiles inside "success".
  6. Suspicion the server lies? Reach for zod-style runtime parsing at the same wrapper seam.
