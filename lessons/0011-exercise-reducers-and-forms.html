Challenge 1 · Lesson 7

Type a filters reducer

Objective: build State, Action union, and reducer from scratch.

A product-list page has filter state: 
interface FiltersState {
  query: string;
  maxPrice: number;
  inStockOnly: boolean;
}
Write:
  • A FiltersAction discriminated union supporting: setting the query, setting the max price, toggling the in-stock flag, resetting everything
  • A fully annotated filtersReducer with an exhaustiveness guard
  • The useReducer wiring (one line)
No any, no optional mega-params.

Solution

type FiltersAction =
  | { type: "setQuery"; value: string }
  | { type: "setMaxPrice"; value: number }
  | { type: "toggleInStock" }
  | { type: "reset" };

const initialFilters: FiltersState = {
  query: "",
  maxPrice: 100,
  inStockOnly: false,
};

function filtersReducer(state: FiltersState, action: FiltersAction): FiltersState {
  switch (action.type) {
    case "setQuery":
      return { ...state, query: action.value };
    case "setMaxPrice":
      return { ...state, maxPrice: action.value };
    case "toggleInStock":
      return { ...state, inStockOnly: !state.inStockOnly };
    case "reset":
      return initialFilters;
    default: {
      const _exhaustive: never = action;
      return state;
    }
  }
}

// In the component — dispatch typed automatically:
const [filters, dispatch] = useReducer(filtersReducer, initialFilters);

Note how payload fields live only where needed: value exists on setQuery/setMaxPrice but not on toggleInStock. Inside each case, TS knows exactly which fields are legal.

Challenge 2 · Lesson 7

Break it on purpose

Objective: predict what the exhaustiveness guard does when violated.

This reducer compiles today: 
type ProductsAction =
  | { type: "sort"; field: "price" | "name" }
  | { type: "shuffle" };
  1. You now add a third variant: | { type: "clear" }. Without touching the switch, describe the error: where does it appear, and what does the message say?
  2. Fix it.

Solution

The error: not at the union definition, and not anywhere you forgot — it appears in the default branch of the switch:

default: {
  const _exhaustive: never = action;
  //    ~~~~~~~~~~~ ← Type '{ type: "clear"; }' is not assignable to type 'never'
  return state;
}

Why: with all cases handled, narrowing had eliminated every member, leaving never in default — so the assignment was legal. The unhandled "clear" survives narrowing into default, and nothing (except never itself) is assignable to never.

The fix: handle it — which is the entire point. The compiler just wrote your TODO list:

case "clear":
  return { items: [], sort: state.sort };
Challenge 3 · Lesson 8

Narrow the form data

Objective: make raw FormData safe to use.

A signup form uses the React 19 action prop: 
<form action={signUp}>
  <input name="name" />
  <input name="email" type="email" />
  <button>Create account</button>
</form>
Write signUp: extract both fields, bail out safely if either is missing or empty (email must contain @), otherwise call api.createUser({ name, email }). No casts, no as.

Solution

async function signUp(formData: FormData): Promise<void> {
  const name = formData.get("name");
  if (typeof name !== "string" || name.trim() === "") return;

  const email = formData.get("email");
  if (typeof email !== "string" || !email.includes("@")) return;

  await api.createUser({ name, email });   // both are guaranteed strings here
}

The key line pattern: typeof x !== "string". After the guard, FormDataEntryValue | null narrows to plain string — same control-flow narrowing as the context guard hook, just with typeof instead of truthiness.

Challenge 4 · Lesson 8

Newsletter form with useActionState

Objective: full production form — errors, pending state, no bugs.

Build a subscribe form:
  • One email input; invalid or missing email → show "Please enter a valid email."
  • Show that error under the form; clear it on a successful retry
  • Disable input + button while submitting, with button text "Subscribing…"
  • Use useActionState — mind the argument order

Solution

import { useActionState } from "react";

interface SubscribeState {
  error: string | null;
}

async function subscribe(
  prevState: SubscribeState,
  formData: FormData
): Promise<SubscribeState> {
  const email = formData.get("email");
  if (typeof email !== "string" || !email.includes("@")) {
    return { error: "Please enter a valid email." };
  }
  await api.subscribe(email);
  return { error: null };
}

function NewsletterForm() {
  const [state, submitAction, isPending] =
    useActionState(subscribe, { error: null });

  return (
    <form action={submitAction}>
      <input name="email" placeholder="you@example.com" disabled={isPending} />
      {state.error && <p role="alert">{state.error}</p>}
      <button disabled={isPending}>
        {isPending ? "Subscribing…" : "Subscribe"}
      </button>
    </form>
  );
}

Three details worth checking yourself on:

  1. (prevState, formData) — state first. The bare action-prop signature is (formData); wrapping flips it.
  2. Every path returns a fresh state object — success resets error: null, so a retry clears the old message.
  3. state's type comes from the initial value — { error: null } infers SubscribeState without a generic annotation.
Stretch · Lessons 5 + 7

App-wide filters: reducer meets Provider

Objective: combine the two lessons into the production scaling pattern.

Turn Challenge 1's reducer into app-wide state:
  • A FiltersProvider holding the reducer
  • Two contexts: one for the state, one for dispatch
  • Guard hooks useFilters() and useFiltersDispatch()
  • Export only Provider + hooks
Then answer: which of these re-renders when the query changes — a badge showing the query, or the reset button?

Solution

import { createContext, useContext, useReducer } from "react";

const FiltersContext = createContext<FiltersState | null>(null);
const FiltersDispatchContext = createContext<React.Dispatch<FiltersAction> | null>(null);

export function FiltersProvider({ children }: { children: React.ReactNode }) {
  const [filters, dispatch] = useReducer(filtersReducer, initialFilters);

  return (
    <FiltersDispatchContext value={dispatch}>
      <FiltersContext value={filters}>{children}</FiltersContext>
    </FiltersDispatchContext>
  );
}

export function useFilters(): FiltersState {
  const ctx = useContext(FiltersContext);
  if (!ctx) throw new Error("useFilters must be used within <FiltersProvider>");
  return ctx;
}

export function useFiltersDispatch(): React.Dispatch<FiltersAction> {
  const ctx = useContext(FiltersDispatchContext);
  if (!ctx) throw new Error("useFiltersDispatch must be used within <FiltersProvider>");
  return ctx;
}

The re-render answer: the badge re-renders (it reads useFilters(), which changed); the reset button does not — it only calls useFiltersDispatch(), and dispatch is the same stable function reference across renders. That's why the split into two contexts is worth its extra three lines.

Note there are no new typing ideas here: Dispatch<FiltersAction> flows through the same honest-null guard-hook shape as every context since Lesson 5.
